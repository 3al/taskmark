# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Общение
- Всегда общайся с пользователем на русском языке.

## Обзор

Канбан-веб-интерфейс поверх Markdown-файлов задач (`tasks/`) для нескольких проектов.
Бэкенд на Python (FastAPI + uvicorn + watchdog) раздаёт закоммиченную сборку React/Vite/Tailwind.
Пользовательская документация на русском — `docs/help/*.md`: её же раздаёт бэкенд в раздел помощи UI
(кнопка «?»), а `README.md` остаётся кратким обзором со ссылками на разделы. Держи их в синхроне
с изменениями поведения; текст пиши в `docs/help/`, а не копией в README.

## Команды

```sh
py taskboard.py                # запуск (Windows); python3 taskboard.py — macOS/Linux
py taskboard.py --dev          # dev-режим: авто-перезагрузка при правках backend/
cd taskboard/frontend && npm install && npm run build   # пересборка фронтенда
cd taskboard/frontend && npm run dev                    # dev-сервер фронта (прокси /api → 127.0.0.1:8765)

# тесты (stdlib unittest), из корня репозитория
taskboard/.venv/Scripts/python.exe -m unittest discover -s taskboard/tests -t taskboard -v
# один тест
taskboard/.venv/Scripts/python.exe -m unittest discover -s taskboard/tests -t taskboard -v -k test_registry
```

- `taskboard.py` сам создаёт `taskboard/.venv` и перезапускается под ним — вручную venv не создавай.
- `-t taskboard` в команде тестов обязателен: модули импортируются как `backend.*` (не `taskboard.backend.*`), потому что лаунчер кладёт `taskboard/` в `sys.path`.
- **Не** используй `uvicorn --reload`: на Windows в связке с watchdog/SSE он зависает при перезапуске, поэтому reload реализован своим супервизором (`taskboard.py:dev_supervisor`).
- Линтера, тайпчека и CI нет. Проверяй изменения запуском сервера.

## Архитектура

- `taskboard.py` — единственная точка входа: bootstrap (Python/venv/deps/dist), логика единственного инстанса, dev-супервизор.
  **Важно при тестировании:** если сервер уже слушает порт, повторный запуск не стартует второй процесс — он регистрирует проект в живом сервере и выходит. Твои правки кода при этом не применятся; останови/перезапусти сервер (UI → Настройки → «Сервер»).
- `taskboard/backend/` — FastAPI:
  - `app.py` — все `/api/*` эндпоинты, монтирование `frontend/dist`, SSE `/api/events`. `CAPABILITIES` — набор возможностей, по которому лаунчер определяет устаревший запущенный сервер.
  - `board_parser.py` / `task_parser.py` — Markdown ⇄ модель. Доска — источник правды: разделы `##` → колонки (статусы), подразделы `###` → группы, строки задач разбираются регуляркой `TASK-NNN · [Заголовок](файл) · агент · дата`.
  - `queue_ops.py` — перемещения (DnD): переписывает строки `board.md` **и** синхронно правит `status` во frontmatter задачи через `set_task_status`. Оба конца должны оставаться согласованными.
  - `registry.py` — мультипроектность (реестр + активный проект).
  - `pipeline_sources.py` — готовые жизненные циклы для заполнения настроек: пресеты (`statuses.PRESETS`) и пайплайны других проектов реестра. Настройки остаются в проекте: скрипты `tasks/*.py` автономны и читают конфиг рядом с собой.
  - `config.py` — дефолты → глобальный конфиг → per-project переопределения.
  - `validator.py` — отчёт о структуре проекта (`critical` / `degraded` / `warnings` / `features`); он же управляет деградацией UI и возвратом 400 из эндпоинтов при критичных проблемах.
  - `scaffold.py` + `taskboard/templates/` — развёртывание структуры `tasks/` и агентского окружения в проекты пользователя. Состав поставки описан реестром `ENV_PARTS` (по нему же валидатор ищет и отсутствие, и устаревание — `environment_issues`), раскладку задаёт выбор сред (`harnesses` в конфиге проекта): claude → `.claude/skills` + `CLAUDE.md`, opencode → `.opencode/commands` + `AGENTS.md`. Скиллы разворачиваются одной копией: в `.opencode/skills` они попадают только в проекте без Claude Code.
  - `migrations.py` — миграции данных проекта при переименовании артефактов в настройках.
  - `watcher.py` — watchdog → SSE-события живых обновлений; включает монитор живости, пересоздающий наблюдателя при молчаливой смерти эмиттера.
  - `help_docs.py` — раздел помощи: читает `docs/help/*.md` (номер в имени файла задаёт порядок,
    остаток — id раздела для deep-link из UI). Источник правды один: те же файлы, на которые
    ссылается README, показывает `HelpModal` во фронтенде.
  - `lifecycle.py` — остановка/перезапуск сервера из UI.
- `taskboard/frontend/src/` — React: вход `main.jsx` → `App.jsx` (состояние доски, вся логика DnD, баннеры отчёта валидации), вызовы API собраны в `api.js`, стили статусов и правила дропа — в `statuses.js`.

## Соглашения и подводные камни

- **Собранный фронтенд закоммичен.** `frontend/dist/` в репозитории — бэкенд раздаёт именно его. Любая правка `frontend/src/` требует `npm run build` и коммита `dist`, иначе изменения не попадут в релиз.
- **Шаблоны — источник правды для агентского окружения.** Скиллы и команды в корне (`.claude/skills/`, `.opencode/commands/`) — это *развёрнутые копии*, полностью игнорируемые git (`*` в их `.gitignore`). Правки скиллов вноси в `taskboard/templates/agentic/.claude/skills/` (и парные обёртки в `.opencode/commands/`), иначе они не доедут до пользователей.
  - Блоки `<!-- vault -->…<!-- /vault -->` в шаблонах скиллов вырезаются при `vault=False`, с автоперенумерацией заголовков «## Шаг N» и ссылок на них.
- **Не хардкодь имена артефактов.** `board.md`, `Queue`, `create_task.py`, `logs/`, статус `queued` — всё конфигурируемо; читай из конфига (`backend/config.py`) и добавляй миграцию в `backend/migrations.py`, если вводишь новое переименуемое имя.
- **Межпроцессная координация через магические константы** — они должны оставаться синхронными: коды выхода `EXIT_STOP=43` / `EXIT_RESTART=42` (дублируются в `taskboard.py` и `backend/lifecycle.py`), env `TASKBOARD_SUPERVISED` и `TASKBOARD_PORT`, маркер остановки `~/.taskboard/stop_<port>.flag`.
- **Глобальное состояние — вне репозитория:** `~/.taskboard/config.json` и `~/.taskboard/projects.json` (per-user). Тесты, трогающие реестр, должны подменять эти пути.
- **Настройки проекта — в `tasks/.taskboard.json`** (жизненный цикл статусов, имена артефактов). Внутри `tasks/`, потому что она игнорируется git и настройки не засоряют репозиторий пользователя; прежний путь `<корень>/taskboard/config.json` читается ради совместимости. Скрипты `tasks/*.py` автономны и читают конфиг сами — меняя расположение, правь и их.
- Порядок колонок — только на фронте, в `localStorage` per-project; с файлом доски не синхронизируется.
- Исходники — UTF-8 с русскими docstring/комментариями и русскими пользовательскими строками (логи, UI). Сохраняй кодировку и существующий русский стиль (Windows PowerShell `Get-Content` может искажать отображение — сами файлы корректные UTF-8).
- Минимум Python 3.10+.

## Workflow задач

- После реализации (тесты зелёные, сервер перезапущен, `dist` пересобран при правках фронта) — **не финализируй и не коммить**: вручную переведи задачу в **testing** (frontmatter + `board.md`), сообщи пользователю суть изменений и попроси проверить результат локально.
- Только после явного подтверждения проверки: коммить изменения и финализируй задачу скиллом `finalize-task` в **completed** (ревью пропускаем: пользователь стеком не владеет).
- `AGENTS.md` содержит те же правила для других агентов — при изменении правил обновляй оба файла.

# TASK MANAGEMENT

Задачи проекта отслеживаются в файлах Markdown в папке tasks/ (gitignored).

## Структура

- tasks/board.md — обзор всех задач по статусам (канбан)
- tasks/TASK-NNN-title.md — отдельная задача
- tasks/epics.md — реестр эпиков (ключ → имя), единый источник имён

## В начале каждой сессии

1. Прочитай tasks/board.md
2. Найди задачу в рабочем статусе (или уточни у пользователя, какую нужно брать)
3. Прочитай файл задачи (frontmatter + описание + чеклист)

## Живая очередь (To Do)

- Задачи для реализации берутся **всегда из раздела `## To Do`** в порядке следования: первая сверху — приоритетная.
- Если в очереди есть задачи — **всегда предлагай взять верхнюю**, не перебирая остальной бэклог.
- Уточняй у пользователя, какую задачу брать, **только если очередь пуста**.

## Жизненный цикл статуса

backlog → todo → development → testing → done  (+ вне маршрута: cancelled)

Порядок задаёт **ожидаемый** маршрут, а не запрет: шаг вперёд через статус (простая
задача, хотфикс) и возврат назад законны. Ближайший следующий статус — рекомендуемый.

Состав настраивается для проекта, поэтому имена статусов **не подставляй по памяти** —
спрашивай у скрипта:

```
py tasks/set_status.py --list             # пайплайн проекта
py tasks/set_status.py --targets TASK-NNN # куда можно двинуть конкретную задачу
```

## Эпики

Эпик объединяет несколько связанных задач. Эпик идентифицируется Jira-ключом (например `E056-18500`).

- Реестр имён: tasks/epics.md — единый источник имени эпика. Имя хранится только здесь.
- В задаче: поле frontmatter epic: <ключ> (или epic: ~ если эпика нет). Имя/ключ эпика не дублируется в заголовок задачи.
- Создание через скилл: /new-task "Название" E056-18500 — скилл регистрирует эпик в epics.md (спрашивает имя при первом упоминании) и проставляет epic: в frontmatter.
- Поиск задач эпика: `grep "epic: E056-18500" tasks/TASK-*.md`

## Смена статуса задачи

Статус хранится в двух местах: поле `status` во frontmatter задачи и раздел в board.md.
**Меняй его только скриптом** — он правит оба места за один вызов, и они не разойдутся:

```
py tasks/set_status.py TASK-004 development --agent "АГЕНТ (модель)"     (Windows)
python3 tasks/set_status.py TASK-004 development --agent "АГЕНТ (модель)"
```

- Статусы проекта: backlog | todo | development | testing | done | cancelled (актуальный список — `set_status.py --list`)
- `--agent` попадает в хвост строки доски вместе с датой; без него сохраняется прежний исполнитель
- `--position end` — вставить в конец раздела (по умолчанию задача встаёт первой)

Править `status:` и board.md руками — только если скрипта в проекте нет.

## Правила работы с задачей

- При начале работы: переведи задачу в рабочий статус (`development`) скриптом `set_status.py`
- Во время работы: добавляй компактные заметки в раздел "Заметки агента"
    - Формат: АГЕНТ (модель): YYYY-MM-DD: ключевое решение/проблема/статус
    - Пример: Claude Sonnet 4.6: 2026-03-02: Найден корень бага в _apply_role_ui()
    - Максимум 1-2 строки на событие, всего макс ~15 строк
    - Цель: Позволить следующей сессии понять контекст, кто и когда работал, на какой модели
- При завершении патча: обнови статус задачи, заполни поле patch: PATCH-NNN-Name
- При каждом коммите по задаче: добавляй строку в секцию «История коммитов» файла задачи (создаётся при первом коммите, если отсутствует — см. шаблон `tasks/_TEMPLATE.md`)
    - Формат: - \`<short-hash>\ <сообщение коммита>` (short-hash — 7 символов из `git rev-parse --short`)
    - Порядок: хронологический (свежие коммиты — в конец списка)
    - Цель: иметь в файле задачи полный последовательный список всех git-коммитов по ней, чтобы быстро поднять историю в гите
    - Покрытие: правило действует во всех скиллах работы с задачей (`start-task`, fix-task, `finalize-task`) и при ручных коммитах
- Важно: Не превращай "Заметки агента" в changelog — это не история коммитов, а компактная помощь следующей сессии понять контекст

## Структура файла задачи

Файл задачи (`tasks/TASK-NNN-*.md`) содержит следующие секции:

- Frontmatter — id, title, epic, status, created, patch
- Описание — что сделать, зачем, критерии приёмки
- Чеклист — список задач для выполнения
- История доработок — *(создаётся скиллом `fix-task`)* фиксирует каждый возврат с ревью: источник замечаний, список замечаний, что доработано, какие файлы изменены
- Заметки агента — компактный лог работы агента над задачей
- История коммитов — *(заполняется при каждом коммите)* последовательный список всех git-коммитов по задаче (short-hash + сообщение), хронологически

## Формат board.md

В каждом разделе статуса (Backlog, To Do, Development, Testing, Done, Cancelled) задачи перечисляются:
- TASK-NNN · [Заголовок](TASK-NNN-название.md) · АГЕНТ (модель) · 2026-MM-DD
  Примеры:
- - TASK-001 · [Fix hard words dict name](TASK-001-fix-hard-words-dict-name-on-profile-switch.md) · Claude Sonnet 4.6 · 2026-03-02

Назначение каждого элемента:
- TASK-NNN — номер задачи
- [Заголовок](файл) — ссылка на файл задачи
- АГЕНТ (модель) — кто последний раз обновлял статус (поможет разобраться в контексте)
- YYYY-MM-DD — дата перевода в этот статус

## Создание новой задачи

### Способ 1: Интерактивный скрипт (рекомендуется)
python3 tasks/create_task.py
Скрипт спросит:
- Название задачи
- Описание
- Критерии приёмки
- Эпик (опционально, Jira-ключ)

Также поддерживает аргументы: -t (название), -d (описание), -c (критерии), -e (эпик).

Затем автоматически:
- Определит следующий номер TASK-NNN
- Создаст файл из шаблона
- Обновит board.md

### Способ 2: Ручное создание

1. Скопировать tasks/_TEMPLATE.md
2. Присвоить следующий номер TASK-NNN
3. Заполнить frontmatter (id, title, epic, created)
4. Добавить в tasks/board.md в раздел приёма задач (Backlog)
