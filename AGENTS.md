# AGENTS.md

## Общение
- Всегда общайся с пользователем на русском языке.

## Обзор
Канбан-веб-интерфейс поверх Markdown-файлов задач (`tasks/`) для нескольких проектов. Стек: бэкенд на Python (FastAPI + uvicorn + watchdog), раздающий закоммиченную сборку React/Vite/Tailwind. Пользовательская документация на русском — `docs/help/*.md` (её же раздаёт кнопка «?» в UI), README.md — краткий обзор со ссылками на неё; держи оба в синхроне с изменениями поведения.

## Команды
- Запуск приложения: `py taskboard.py` (Windows) / `python3 taskboard.py` — сам создаёт `taskboard/.venv` и перезапускается под ним; не создавай venv вручную.
- Dev-режим бэкенда с авто-перезагрузкой: `py taskboard.py --dev` (свой супервизор; **не** используй `uvicorn --reload` — на Windows он зависает в связке с watchdog/SSE, см. комментарий в `taskboard.py:dev_supervisor`).
- Пересборка фронтенда: `cd taskboard/frontend && npm install && npm run build` — `frontend/dist/` **закоммичен**; бэкенд раздаёт его, поэтому изменения фронтенда нужно пересобрать и закоммитить dist, иначе они не попадут в релиз.
- Dev-сервер фронтенда: `npm run dev` в `taskboard/frontend` (проксирует `/api` на `127.0.0.1:8765`).
- Тесты (stdlib unittest): `taskboard/.venv/Scripts/python.exe -m unittest discover -s taskboard/tests -t taskboard -v` из корня репо. Линтера, тайпчека и CI нет. Проверяй изменения запуском сервера.
- История выпусков: `py tools/release.py --history` — JSON с версией, тегом, временем выпуска и составом задач, от свежего к старому. **Про выпуски не гадай по коммитам.** Скрипт только читает git; в поставку пользователям он не идёт, у них выпуск устроен по-своему.

## Архитектура
- `taskboard.py` — единственная точка входа: bootstrap (проверки venv/deps/dist), логика единственного инстанса, супервизор. Если сервер уже слушает порт, второй запуск просто регистрирует проект и выходит — учитывай это при тестировании.
- `taskboard/backend/` — FastAPI-приложение. Ключевые модули: `board_parser.py`/`task_parser.py` (Markdown ⇄ модель), `queue_ops.py` (DnD-мутации), `registry.py` (мультипроектность), `pipeline_sources.py` (готовые жизненные циклы: пресеты и пайплайны других проектов), `scaffold.py` + `taskboard/templates/` (развёртывание структуры `tasks/`, агентского окружения и опционального волта `vault/`; состав поставки — реестр `ENV_PARTS`, раскладка — выбор сред `harnesses` и флаг `vault` в конфиге проекта), `watcher.py` (watchdog → SSE живые обновления), `lifecycle.py` (остановка/перезапуск из UI), `help_docs.py` (раздача разделов помощи из `docs/help/`).
- `taskboard/frontend/src/` — React-приложение; вход `main.jsx` → `App.jsx`; вызовы API собраны в `src/api.js`.

## Workflow задач
- **Значимая для пользователя правка — обнови руководство.** Меняется то, что пользователь видит или делает (новая возможность, поведение UI, кнопки и баннеры, формат его файлов, порядок работы) — правка `docs/help/*.md` входит в задачу, а не откладывается: справку раздаёт сам инструмент, и устаревшая справка врёт прямо в интерфейсе. Заодно проверь README (он ссылается на те же разделы). Чисто внутренние изменения (рефакторинг, тесты, детали реализации) руководства не касаются.
- **Правки шаблонов не разворачивай в этот репозиторий.** Тронул `taskboard/templates/` (скиллы, `rules_section.md`, скрипты `tasks/*.py`, файлы волта) — правь **только шаблон**, а развёрнутые копии (`.claude/skills/`, `.opencode/`, `CLAUDE.md`, `AGENTS.md`, `tasks/*.py`, `vault/SYS/`) оставь как есть: не запускай scaffold и не переписывай их руками. Возникшее расхождение — часть проверки: пользователь должен увидеть баннер устаревания, посмотреть diff и обновить кнопкой. Заровняв его, ты прячешь именно то, что он проверяет.
- После реализации (тесты зелёные, сервер перезапущен, dist пересобран при правках фронта, руководство обновлено) — **не финализируй и не коммить**: вручную переведи задачу в **testing** (frontmatter + board.md), сообщи пользователю суть изменений и попроси проверить результат локально.
- Только после явного подтверждения проверки: коммить изменения и финализируй задачу скиллом finalize-task в **completed** (ревью пропускаем: пользователь стеком не владеет).

## Соглашения и подводные камни
- Исходники — UTF-8 с русскими docstring/комментариями и русскими пользовательскими строками (логи, UI). Сохраняй кодировку при редактировании (Windows PowerShell `Get-Content` может искажать отображение — сами файлы корректные UTF-8). Придерживайся существующего русского стиля.
- Межпроцессная координация через магические константы и env-переменные, которые должны оставаться синхронными: коды выхода `EXIT_STOP=43` / `EXIT_RESTART=42` (дублируются в `taskboard.py` и `backend/lifecycle.py`), env `TASKBOARD_SUPERVISED`, `TASKBOARD_PORT`, маркер остановки `~/.taskboard/stop_<port>.flag`.
- Глобальное состояние живёт в `~/.taskboard/` (`config.json`, `projects.json`) — per-user, вне репозитория.
- Настройки проекта — в `tasks/.taskboard.json` (жизненный цикл статусов, выбранные среды): внутри `tasks/`, которая игнорируется git. Прежний путь `<корень>/taskboard/config.json` читается ради совместимости. Скрипты `tasks/*.py` автономны и читают конфиг сами.
- Имена системных артефактов (`board.md`, `create_task.py`, `set_status.py`, `logs/`, `Queue`, статус `queued`) — константы поставки, а не настройка: переименование доезжало до данных, но не до текстов скиллов и правил, где имена зашиты (TASK-053). Значения лежат в `DEFAULTS` (`backend/config.py`), код читает их оттуда — новых переименуемых имён не вводи.
- Минимум Python 3.10+.

# TASK MANAGEMENT

Задачи проекта отслеживаются в файлах Markdown в папке tasks/ (gitignored).

## Структура

- tasks/board.md — обзор всех задач по статусам (канбан)
- tasks/TASK-NNN-title.md — отдельная задача
- tasks/epics.md — реестр эпиков (ключ → имя), единый источник имён

## Чем запускать скрипты

Дальше команды написаны через `py` (Windows) и `python3` (macOS/Linux) —
это самые частые варианты, но **не единственные**. Лаунчера `py` может не быть:
Python из Microsoft Store его не ставит, и вызов падает с
`CommandNotFoundException`.

Команда не найдена — **не бросай скрипт, попробуй соседнюю**:

```
py tasks/set_status.py --list        # Windows с лаунчером
python tasks/set_status.py --list    # Windows из Microsoft Store, окружения без py
python3 tasks/set_status.py --list   # macOS/Linux
```

Какая сработала — той и пользуйся дальше в сессии.

## В начале каждой сессии

1. Прочитай tasks/board.md
2. Найди задачу в рабочем статусе (или уточни у пользователя, какую нужно брать)
3. Прочитай файл задачи (frontmatter + описание + критерии приёмки)

## Живая очередь (To Do)

- Задачи для реализации берутся **всегда из раздела `## To Do`** в порядке следования: первая сверху — приоритетная.
- **Очередь не называй по памяти** — ни когда предлагаешь задачу, ни мимоходом
  в отчёте («дальше в очереди…»). Доску правят через UI и другие агенты, снимок
  из начала сессии устаревает молча. Спрашивай у скрипта прямо перед ответом:

  ```
  py tasks/set_status.py --queue             # верхушка очереди (Windows)
  python3 tasks/set_status.py --queue
  py tasks/set_status.py --queue --limit 0   # вся очередь
  ```

- Если в очереди есть задачи — **всегда предлагай взять верхнюю**, не перебирая остальной бэклог.
- Уточняй у пользователя, какую задачу брать, **только если очередь пуста**.
- **Стоящие задачи пропускай**: у каждой записи среза есть `stalled` — верхняя
  свободная и есть следующая в работу (см. «Почему задача стоит»).

## Почему задача стоит: блокировки и пауза

У задачи одно производное состояние — **«стоит»** — и две причины:

- `blocked_by: TASK-NNN[, TASK-MMM]` — ждёт другую задачу;
- `paused: <причина>` — ждёт внешнего обстоятельства.

Третье поле, `blocks`, — обратный конец зависимости: у блокера перечислено, кого
он держит. Во всех трёх `~` и пусто означают «нет». **Пауза — метка, а не
статус**: задача остаётся на своём этапе.

**Не бери стоящую задачу в работу.** Пользователь может перенести её мышью,
подтвердив вопрос на доске; у тебя такого подтверждения нет — предложи верхнюю
свободную из очереди и скажи, чего ждёт пропущенная. Скрипт это подстрахует:
перевод стоящей задачи в рабочий статус без `--force` не выполнится.

Простой правится **только скриптом** — зависимость живёт двумя концами, и он
пишет **обе** стороны за один вызов:

```
py tasks/set_status.py TASK-014 --block TASK-013     # TASK-014 ждёт TASK-013
py tasks/set_status.py TASK-014 --unblock TASK-013   # снять одну; без значения — все
py tasks/set_status.py TASK-014 --pause "ждём ответ контрагента"
py tasks/set_status.py TASK-014 --resume
py tasks/set_status.py --stalled                     # что стоит и почему (JSON)
```

- **Ставить простой можно не всегда**: у завершённой или отменённой задачи «ждёт»
  смысла не имеет — скрипт откажет. Снять можно в любом статусе.
- **Переезд в конец маршрута снимает простой сам** — вместе с обратными ссылками.
- Блокер, который сам дошёл до конца маршрута, больше не держит: снимай пометку
  (`--unblock`), не жди, что она исчезнет. Искать такие пометки самому не надо —
  скрипт считает их сам: в очереди и срезе у задачи стоит `stale` с причиной,
  стоящей она не считается, а старт из-за неё не отказывает.
- **Отменённый блокер держит не больше выполненного, но говорит другое**: вместе
  с ним мог отпасть и предмет самой задачи — проверь это, прежде чем начинать.

## Жизненный цикл статуса

backlog → todo → development → testing → ready_for_release → release_notes → to_release → done  (+ вне маршрута: cancelled)

Порядок задаёт **ожидаемый** маршрут, а не запрет: шаг вперёд через статус (простая
задача, хотфикс) и возврат назад законны. Ближайший следующий статус — рекомендуемый.

Состав настраивается для проекта, поэтому имена статусов **не подставляй по памяти** —
спрашивай у скрипта:

```
py tasks/set_status.py --list             # пайплайн проекта
py tasks/set_status.py --targets TASK-NNN # куда можно двинуть конкретную задачу
```

## Эпики

Эпик объединяет несколько связанных задач. Эпик идентифицируется Jira-ключом (например `E056-18500`).

- Реестр имён: tasks/epics.md — единый источник имени эпика. Имя хранится только здесь.
- В задаче: поле frontmatter epic: <ключ> (или epic: ~ если эпика нет). Имя/ключ эпика не дублируется в заголовок задачи.
- Создание через скилл: /new-task "Название" E056-18500 — скилл регистрирует эпик в epics.md (спрашивает имя при первом упоминании) и проставляет epic: в frontmatter.
- Состав эпика — **одной командой**, а не грепом: `py tasks/set_status.py --epic E056-18500`
  (`python3` — macOS/Linux). Возвращает JSON: номер, статус, подпись статуса и заголовок
  каждой задачи в порядке маршрута. Ключ с опечаткой даёт ошибку с перечнем эпиков реестра,
  а не пустой список.

## Knowledge Vault (vault/)

Внешняя память проекта: знания, добытые в одной задаче, переиспользуются в следующих.

- Структура: `vault/SYS/` — правила ведения (`structure.md`), шаблоны заметок, таксономия тегов; остальные папки — домены проекта.
- Типы заметок: `business` (что и зачем, бизнес-правила) и `code` (файлы, поток данных, паттерны). Для новой фичи создаются **обе** и ссылаются друг на друга.
- Чтение: при старте задачи загляни в `vault/SYS/taxonomy.md` и заметки подходящего домена — это дешевле, чем вычитывать код заново.
- Запись: **отдавая задачу на проверку** (скилл `handoff-task`) сохраняй новые знания скиллом `write-vault` — пока контекст жив. Позже, к закрытию задачи и тем более к выпуску, деталей не помнит никто, и заметка выходит отпиской вместо знания. Критерий: если в следующей задаче на ту же тему пришлось бы заново изучать тот же код — знание стоит записать.
- Теги только из `vault/SYS/taxonomy.md`; новый тег сначала добавляется туда.

**Папка `vault/` в .gitignore, и обычный поиск её не видит.** glob/grep пропускают
игнорируемые файлы, поэтому волт покажется пустым. Работают: явные пути (`ls vault/*/`,
чтение файла по пути) и поиск с отключённым ignore-фильтром — `rg --no-ignore "<слово>" vault/`.

## Смена статуса задачи

Статус хранится в двух местах: поле `status` во frontmatter задачи и раздел в board.md.
**Меняй его только скриптом** — он правит оба места за один вызов, и они не разойдутся:

```
py tasks/set_status.py TASK-004 development --agent "АГЕНТ (модель)"     (Windows)
python3 tasks/set_status.py TASK-004 development --agent "АГЕНТ (модель)"
```

- Статусы проекта: backlog | todo | development | testing | ready_for_release | release_notes | to_release | done | cancelled (актуальный список — `set_status.py --list`)
- `--agent` попадает в хвост строки доски вместе с датой; без него сохраняется прежний исполнитель
- `--position end` — вставить в конец раздела (по умолчанию задача встаёт первой)

**Статус меняется в тот момент, который он описывает.** «Взял в работу» — первым
действием, до реализации: иначе доска врёт, что задача свободна. «Закончил» —
**последним**, когда файл задачи уже приведён в порядок: «История коммитов»
заполнена, знание записано, план (если вёл) закрыт. Причины две:

- статус — публикация факта, и публиковать его раньше правды нельзя;
- требования этапа проверяются ровно в момент перехода, поэтому незакрытое
  остановит перевод — чинить это надо до вызова, а не после отказа.

**Подтверждение человека — не строчка в переписке.** Сказал «проверил», «всё
ок», «замечаний нет» — отметь это сразу, его словами: иначе подтверждение умрёт
вместе с сессией, а этап останется незакрытым.

```
py tasks/set_status.py TASK-004 --confirm verified "проверил локально, замечаний нет"
```

Имя требования (`verified` в примере) называет сам скрипт — при входе на этап и
в отказе. **Сам за человека не подтверждай**: отметка фиксирует чужое слово, а
не заменяет его.

**Отмена требует причины.** Съезд с маршрута терминален: из него не
возвращаются, и «почему» должно остаться в файле. Без `--reason` скрипт
откажет, причина ляжет в поле `cancel_reason`:

```
py tasks/set_status.py TASK-004 cancelled --reason "дублирует TASK-002"
```

Причину не выдумывай — спроси у пользователя, если он её не назвал.

Править `status:` и board.md руками — только если скрипта в проекте нет.

## Чеклист задачи

Чеклист — **план под конкретную работу**, а не обязательная часть задачи. Шаблон
его не ставит: заводи секцию `## Чеклист` сам, когда работа многошаговая и её
состояние нужно передать следующей сессии. **Нет плана — нет секции.**

- Пункты пиши по предстоящей работе, а не по типу задачи: «вынести парсер»,
  «проверить на тёмной теме» — то, что действительно будешь делать.
- Пункт, который выполняться не будет, **удаляют, а не отмечают**: закрытая
  галочка означает сделанное, и ритуальная отметка лишает смысла все соседние.
- Место секции — после «Описания», перед «Комментариями» (эталон —
  `tasks/_TEMPLATE.md`).
- Незакрытые пункты скрипт назовёт сам, когда работа кончится. Секции нет —
  промолчит: спрашивать план с того, кто его не вёл, незачем.

## Тип задачи

Тип отвечает на вопрос «что это за работа»: он живёт в поле `type:` задачи,
рисует метку на доске (кружок с буквой на превью, подпись целиком в открытой
задаче) и задаёт исключения в требованиях этапа.

**Имена типов не подставляй по памяти** — спроси у скрипта:

```
py tasks/set_status.py --types             (Windows)
python3 tasks/set_status.py --types
```

- Ставится при создании: `create_task.py --type <тип>` (по умолчанию — `feature`)
- Правится тем же скриптом, что и остальное: `set_status.py TASK-NNN --type <тип>`
- **Тип — не этап**: по маршруту он задачу не двигает и статус не трогает
- Задача, заведённая до появления поля, метки не имеет — это не ошибка, а
  отсутствие данных; проставь тип, если он нужен

## Размер задачи

Размер отвечает на другой вопрос — «сколько тут работы»: он живёт в поле
`size:`, показывается буквами на карточке и на доске по нему отбирают задачи.

**Значения не подставляй по памяти** — спроси у скрипта, он же поясняет, чем
один размер отличается от соседнего:

```
py tasks/set_status.py --sizes             (Windows)
python3 tasks/set_status.py --sizes
```

- **Ставится при взятии в работу**, когда контекст изучен: при заведении задачи
  оценку строить не на чем, а к концу работы она уже не нужна
- Правится тем же скриптом: `set_status.py TASK-NNN --size <размер>`; пустое
  значение снимает оценку
- **Размер — не этап и не тип**: по маршруту он задачу не двигает и вид работы
  не описывает
- Ошибся в оценке — **поправь**, а не оставляй: смена уходит в хронологию и
  объясняет следующей сессии, почему работа затянулась
- Задача без размера — норма: оценки просто ещё не было

## Исполнитель задачи

Исполнитель отвечает на вопрос «кто занимается задачей **сейчас**»: он живёт в
поле `assignee:` и спрашивается не на каждом этапе, а только там, где проект
поставил галочку «исполнитель» (обычно ревью и тестирование).

**Этап, спрашивающий исполнителя, без имени не пропустит.** Перевод туда — тот
момент, когда имя нужно назвать:

```
py tasks/set_status.py TASK-014 testing --agent "Модель" --assignee "Иванов"
python3 tasks/set_status.py TASK-014 testing --agent "Модель" --assignee "Иванов"
```

- **Имя выдумывать нельзя — его знает только человек.** Отказ скрипта означает
  «спроси, кто займётся задачей», а не «подставь кого-нибудь». Известные имена
  подскажет `set_status.py --assignees` — предложи их человеку на выбор.
- Список имён **общий для всех проектов машины** и пополняется сам: назначенное
  впервые имя дальше предлагается везде.
- **Снять назначение можно в любом статусе** (`--assignee ""`): задачу могли
  перенести с этапа проверки, и застрявшее имя надо убирать.
- На этапе, который исполнителя не спрашивает, назначить его нельзя — скрипт
  откажет. Где спрашивают, настраивает человек, а не ты.
- Незаполненное имя на таком этапе — **долг**: он виден на карточке и никуда не
  денется, пока исполнителя не назовут.

## Правила работы с задачей

- При начале работы: переведи задачу в рабочий статус (`development`) скриптом `set_status.py`
- Во время работы: добавляй компактные комментарии в раздел «Комментарии» — **тем же скриптом**:

  ```
  py tasks/set_status.py TASK-004 --note "суть" --agent "Модель"     (Windows)
  python3 tasks/set_status.py TASK-004 --note "суть" --agent "Модель"
  ```

    - **Время ставит скрипт, из системы.** Выдумать его нельзя — а выдуманное как раз и ломало порядок: комментарии, дописанные пачкой в конце работы, получали время «на глаз»
    - **Новый комментарий идёт в конец секции**: комментарии — хронология, старые сверху, свежие снизу. Порядок не переставляй и прежние строки не переписывай
    - **`--agent` обязателен: модель указывай свою**, не скопированную из соседней строки, — иначе история врёт о том, кто что делал. Имя бери из текущей сессии, а не из файла задачи
    - **Пиши по ходу работы, а не пачкой в конце** — время в строке означает момент события
    - **Перевод статуса комментировать не нужно**: строку `Было → Стало` скрипт пишет сам, и подписывает её источником перехода. Комментарий рядом нужен, только когда есть что сказать сверх факта перехода
    - **Действия по задаче скрипт тоже записывает сам** — блокировка и пауза (обоим концам зависимости), смена типа, переименование. Дублировать их комментарием не надо: строка уже есть, и вторая делает хронологию шумной
    - Формат строки скрипт собирает сам — `- **ГГГГ-ММ-ДД ЧЧ:ММ** · Модель · суть`:

      - **2026-03-02 23:59** · Claude Sonnet 4.6 · корень бага в _apply_role_ui(): роль читалась до применения темы

    - Максимум 1–2 строки на событие, всего ~15 строк
    - Цель: следующая сессия понимает контекст — кто, когда и на какой модели работал
    - Скрипта в проекте нет — пиши строку руками в том же формате: **отдельной строкой списка** (соседние строки без дефиса markdown склеивает в один нечитаемый абзац), время из системы (`date +%H:%M`), в конец секции
- **Заголовки секций — структура файла, а не оформление.** Не сноси и не переименовывай их, порядок держи как в `tasks/_TEMPLATE.md`, а «История коммитов» остаётся **последней** секцией файла. Нет секции — верни заголовок, а не пиши текст в соседнюю
- Смена статуса заодно проверяет файл задачи и печатает `[!] …`, если секции разъехались или комментарии не в хронологии. Это про твою работу — увидел, почини сразу
- При каждом коммите по задаче: добавляй строку в секцию «История коммитов» файла задачи (создаётся при первом коммите, если отсутствует — см. шаблон `tasks/_TEMPLATE.md`)
    - Формат: - \`<short-hash>\ <сообщение коммита>` (short-hash — 7 символов из `git rev-parse --short`)
    - Порядок: хронологический (свежие коммиты — в конец списка)
    - Цель: иметь в файле задачи полный последовательный список всех git-коммитов по ней, чтобы быстро поднять историю в гите
    - Покрытие: правило действует во всех скиллах работы с задачей (`start-task`, `handoff-task`, fix-task, `finalize-task`) и при ручных коммитах
- Важно: Не превращай "Комментарии" в changelog — это не история коммитов, а компактная помощь следующей сессии понять контекст

## Как писать текст задачи

Задачу читает человек — в файле и в окне доски. Сплошная простыня на десять
строк нечитаема, даже если написана по делу.

- **Абзац — одна мысль.** Между абзацами **пустая строка**: одиночный перенос
  markdown склеивает, поэтому строки без разрыва сливаются в простыню. Внутри
  абзаца переносить можно — на рендер это не влияет.
- **Перечисления — списком**, а не запятыми внутри предложения: варианты,
  условия, шаги, затронутые файлы.
- **Акценты разметкой**: `**жирным**` — ключевое решение и ограничение,
  `` `код` `` — имена файлов, функций, полей, статусов, команд.
- **Длинное описание — с подзаголовками** (`###`): «Контекст», «Что делаем»,
  «Границы». Короткому хватает пары абзацев.
- **Не пиши в описание ход работы** — для него есть «Комментарии».

Это правило действует и когда задачу заводит агент, и когда текст пришёл от
пользователя одной строкой: приведи его в читаемый вид, не меняя смысла.

**Задачу, заведённую человеком через форму, оформляет тот, кто берёт её в работу** —
первым делом при старте, до реализации. Меняется только разметка: формулировки
автора остаются дословно, непонятные места уточняются вопросом, а не догадкой.

## Структура файла задачи

Файл задачи (`tasks/TASK-NNN-*.md`) содержит следующие секции:

Эталон структуры — `tasks/_TEMPLATE.md`: его копируют при ручном создании задачи,
по нему же `create_task.py` собирает новую. Правится шаблон — меняются и новые задачи.

- Frontmatter — id, title, epic, type, status, created (дата и время), blocked_by
- Описание — что сделать и зачем; внутри подраздел «Критерии приёмки» — проверяемый результат
- Замечания ревью — *(создаётся скиллом `review-task`)* результат разбора чужого кода: блокирующие отдельно от необязательных, у каждого замечания место, суть и источник
- Чеклист — *(необязательная, заводит агент)* план работы под эту задачу
- История доработок — *(создаётся скиллом `fix-task`)* фиксирует каждый возврат с ревью: источник замечаний, список замечаний, что доработано, какие файлы изменены
- Комментарии — компактный лог работы над задачей: пишет агент, пишет и человек с доски
- История коммитов — *(заполняется при каждом коммите)* последовательный список всех git-коммитов по задаче (short-hash + сообщение), хронологически

## Формат board.md

В каждом разделе статуса (Backlog, To Do, Development, Testing, Ready for Release, Release Notes, To Release, Done, Cancelled) задачи перечисляются:
- TASK-NNN · [Заголовок](TASK-NNN-название.md) · АГЕНТ (модель) · 2026-MM-DD
  Примеры:
- - TASK-001 · [Fix hard words dict name](TASK-001-fix-hard-words-dict-name-on-profile-switch.md) · Claude Sonnet 4.6 · 2026-03-02

Назначение каждого элемента:
- TASK-NNN — номер задачи
- [Заголовок](файл) — ссылка на файл задачи
- АГЕНТ (модель) — кто последний раз обновлял статус (поможет разобраться в контексте)
- YYYY-MM-DD — дата перевода в этот статус

## Создание новой задачи

### Способ 1: Интерактивный скрипт (рекомендуется)
python3 tasks/create_task.py
Скрипт спросит:
- Название задачи
- Описание
- Критерии приёмки
- Эпик (опционально, Jira-ключ)

Также поддерживает аргументы: -t (название), -d (описание), -c (критерии),
-e (эпик), --type (тип задачи, см. «Тип задачи»).

Затем автоматически:
- Определит следующий номер TASK-NNN
- Создаст файл из шаблона
- Обновит board.md

### Способ 2: Ручное создание

1. Скопировать tasks/_TEMPLATE.md
2. Присвоить следующий номер TASK-NNN
3. Заполнить frontmatter (id, title, epic, type, created)
4. Добавить в tasks/board.md в раздел приёма задач (Backlog)
