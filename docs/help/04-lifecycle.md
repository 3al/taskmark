# Жизненный цикл задач

Набор статусов у каждого проекта свой: где-то нет ревью, где-то нужен отдельный статус
ожидания стенда или релиза. Он настраивается в **Настройки (⚙) → Жизненный цикл задачи**
и хранится в конфиге проекта — `tasks/.taskboard.json` (внутри `tasks/`, которая
игнорируется git, поэтому настройки не попадают в репозиторий).

Настройки живут в самом проекте намеренно: скрипты `tasks/*.py` автономны и читают
конфиг рядом с собой, поэтому маршрут переезжает вместе с проектом и не теряется
на другой машине. Чтобы не вводить один и тот же маршрут в десятый раз, в редакторе
есть **«Взять готовый маршрут»**: встроенные пресеты (простой, с ревью, полный, с релизами) и
пайплайны других проектов реестра — тех, у кого настроен свой. Выбор подставляет
статусы, действия и подписи в форму; применяется всё обычным «Сохранить», с тем же
переносом задач из выключаемых статусов.

## Как собрать свой пайплайн

Статусы берутся из готового набора: `backlog`, `todo`, `queued`, `to_fix`, `development`,
`local_testing`, `review`, `to_testing`, `testing`, `ready_for_release`,
`release_notes`, `to_release`, `ready_to_deploy`, `completed`, `done`,
`cancelled`. В редакторе можно включать нужные, убирать лишние и менять порядок стрелками.

**Порядок в списке — это маршрут задачи.** Что правее текущего статуса — «вперёд», что левее —
«назад». Отсюда берутся колонки доски и подсказки скиллов.

### Если вы выпускаете версии

Для этого случая в наборе есть три статуса подряд, и они решают задачу, которую один
статус не решает: **проверенных задач копятся десятки, а в ближайший выпуск едут не все.**

- **Готово к выпуску** — проверено, может поехать. Пул, задача ждёт здесь сколько угодно.
- **Заметки о релизе** — отобрано в готовящийся выпуск, пишется текст изменения
  для пользователей.
- **В ближайший релиз** — текст вычитан и утверждён, задача точно едет.

Отдельно от них — **К деплою**: выкатка на стенд или прод, а не выпуск версии. Это разные
процессы, и в одном пайплайне обычно нужен только один из них.

Готовый маршрут с этими статусами — пресет **«С релизами»**. Как проходит сам выпуск
и как подключить свой скрипт — в разделе [«Выпуск версий»](08-release.md).

Действия говорят, куда скиллы ведут задачу:

| Действие | Что означает | Кто использует |
|---|---|---|
| Новая задача | куда попадает созданная задача | `create_task.py`, кнопка «+» в UI |
| Брать работу из | раздел живой очереди | `start-task` |
| Взять в работу | рабочий статус | `start-task` |
| Вернуть после замечаний | куда возвращают с проверки | `fix-task` |
| Готовить заметки релиза | куда попадает отобранное в выпуск | скилл выпуска |
| Отобрано в релиз | состав, тексты которого утверждены | скилл выпуска |

Первые четыре нужны всем. **Последние два — только тем, кто выпускает версии**; в форме
у них есть вариант «не используется», и по умолчанию они пусты.

Пример конфига для флоу с ревью, стендом и релизом:

```json
{
  "pipeline": ["backlog", "todo", "to_fix", "development",
               "review", "to_testing", "testing", "ready_to_deploy", "done", "cancelled"],
  "actions": { "create": "backlog", "pick": "todo",
               "start": "development", "return": "to_fix" }
}
```

Свой статус, которого нет в наборе, тоже можно завести — достаточно описать оформление:

```json
"statuses": { "hotfix_wait": { "label": "Ждёт окна", "section": "Hotfix Wait", "color": "rose" } }
```

## Правила движения

Запретов нет: пайплайн описывает **ожидаемый** маршрут, а не забор. Простую задачу можно
двинуть из разработки сразу в тестирование, а ночной хотфикс — сразу в завершённые.
Ближайший следующий статус скиллы и UI предлагают первым, остальные доступны без церемоний.
Мягкое ограничение для мыши на доске (чтобы карточка не уехала случайным
движением) регулируется галкой «DnD по всей доске» в настройках — по умолчанию
она включена, и ограничения нет.

Два статуса ведут себя особо:

- **`cancelled`** — вне маршрута: перевести в него можно из любого статуса, но как
  «следующий шаг» он не предлагается никогда
- **`to_fix`** — статус возврата, поэтому стоит левее разработки: попадание в него из
  тестирования читается как движение назад, а «вперёд» из тестирования ведёт к релизу

## Что происходит при изменении пайплайна

- включили статус — раздел появляется в `board.md` на своём месте по порядку;
- выключили пустой — раздел убирается;
- выключили статус с задачами — UI спросит, куда их перенести, и подвинет и строки доски,
  и `status:` во frontmatter файлов задач;
- секция правил в `AGENTS.md` / `CLAUDE.md` пересобирается под новый маршрут.

## Смена статуса вручную и агентами

```sh
# py — лаунчер Windows; нет его (Python из Microsoft Store) — зовите python,
# на macOS/Linux — python3
py tasks/set_status.py TASK-004 development --agent "Имя (модель)"
python tasks/set_status.py TASK-004 development --agent "Имя (модель)"
py tasks/set_status.py --list              # пайплайн проекта
py tasks/set_status.py --targets TASK-004  # куда можно двинуть задачу
py tasks/set_status.py --queue             # очередь прямо сейчас (--limit 0 — вся)
py tasks/set_status.py TASK-004 --note "суть" --agent "Имя (модель)"  # заметка агента
```

Скрипт правит `status:` в файле задачи и строку в `board.md` за один вызов — руками
их лучше не разводить. Он же пишет заметки агента (`--note`): время берёт из системы,
строку ставит в конец раздела «Заметки агента» — подробнее в разделе «Структура». Скиллы (`start-task`, `fix-task`, `finalize-task`) имён статусов
не содержат: они спрашивают их у скрипта, поэтому подстраиваются под пайплайн проекта сами.

`--queue` отвечает на вопрос «что брать следующим»: раздел очереди в порядке
следования, каким он стал **сейчас**. Агенту это важнее, чем вам: пока он работал
над задачей, вы могли переставить приоритеты на доске, и очередь, названная
по памяти сессии, оказалась бы устаревшей. Правила требуют спрашивать её этой
командой, а не пересказывать прочитанное в начале работы.

## Когда работа над задачей кончается

С релизным хвостом последний статус наступает не тогда, когда исполнитель
закончил: задача уходит в пул готового и ждёт выпуска, а закрывает её уже релизный
скилл — днями позже и в другой сессии. Поэтому всё, что делается «в конце»
(сохранить знание в волт, проставить чеклист, вписать коммиты), делается **раньше** —
когда задача покидает работу.

Момент вычисляется по вашему маршруту, а не по имени статуса:

- **есть статус подготовки текстов релиза** — работа кончается в статусе перед ним;
- **нет** — работа кончается в последнем статусе маршрута.

При переходе именно туда `set_status.py` печатает `[!]` с тем, что осталось:

```
[!] работа над задачей кончилась — что выяснилось про проект, сохраните в волт …
[!] незакрытых пунктов чеклиста: 2 — «Написать тест», «Обновить справку»
[!] секция «История коммитов» пуста: по строке на коммит задачи …
[!] задачу ждут: TASK-039 — их пометки снимают у них: --unblock TASK-041
```

Проверяемое скрипт проверяет сам, поэтому называет конкретные пункты, а не общую
фразу. Про волт он может только напомнить — стоит ли сохранять знание, решает
человек; тем, у кого волта нет, про него и не говорится.

Это подсказка, а не запрет: переход выполняется в любом случае.
