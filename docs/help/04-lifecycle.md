# Жизненный цикл задач

Набор статусов у каждого проекта свой: где-то нет ревью, где-то нужен отдельный статус
ожидания стенда или релиза. Он настраивается в **Настройки (⚙) → Жизненный цикл**
и хранится в конфиге проекта — `tasks/.taskboard.json` (внутри `tasks/`, которая
игнорируется git, поэтому настройки не попадают в репозиторий).

Настройки живут в самом проекте намеренно: скрипты `tasks/*.py` автономны и читают
конфиг рядом с собой, поэтому маршрут переезжает вместе с проектом и не теряется
на другой машине. Чтобы не вводить один и тот же маршрут в десятый раз, в редакторе
есть **«Взять готовый маршрут»**: встроенные пресеты (простой, с ревью, полный, с релизами) и
пайплайны других проектов реестра — тех, у кого настроен свой. Выбор подставляет
в форму весь жизненный цикл источника: статусы, действия, подписи и требования
этапов. Применяется всё обычным «Сохранить», с тем же переносом задач из
выключаемых статусов.

## Как собрать свой пайплайн

Статусы берутся из готового набора: `backlog`, `todo`, `queued`, `to_fix`, `development`,
`local_testing`, `review`, `to_testing`, `testing`, `ready_for_release`,
`release_notes`, `to_release`, `ready_to_deploy`, `completed`, `done`,
`cancelled`. В редакторе можно включать нужные, убирать лишние и менять порядок стрелками.

**Порядок в списке — это маршрут задачи.** Что правее текущего статуса — «вперёд», что левее —
«назад». Отсюда берутся колонки доски и подсказки скиллов.

### Если вы выпускаете версии

Для этого случая в наборе есть три статуса подряд, и они решают задачу, которую один
статус не решает: **проверенных задач копятся десятки, а в ближайший выпуск едут не все.**

- **Ready for Release** — проверено, может поехать. Пул, задача ждёт здесь сколько угодно.
- **Release Notes** — отобрано в готовящийся выпуск, пишется текст изменения
  для пользователей.
- **To Release** — текст вычитан и утверждён, задача точно едет.

Отдельно от них — **Ready to Deploy**: выкатка на стенд или прод, а не выпуск версии. Это разные
процессы, и в одном пайплайне обычно нужен только один из них.

Через все четыре агент не ведёт задачи типов «Обсуждение» и «Код-ревью»:
выпускать по ним нечего, и следующим шагом он предлагает закрытие
(см. [«Тип задачи»](03-structure.md)).

Готовый маршрут с этими статусами — пресет **«С релизами»**. Как проходит сам выпуск
и как подключить свой скрипт — в разделе [«Выпуск версий»](08-release.md).

Действия говорят, куда скиллы ведут задачу:

| Действие | Что означает | Кто использует |
|---|---|---|
| Новая задача | куда попадает созданная задача | `create_task.py`, кнопка «+» в UI |
| Брать работу из | раздел живой очереди | `start-task` |
| Взять в работу | рабочий статус | `start-task` |
| Вернуть после замечаний | куда возвращают с проверки | `fix-task` |
| Готовить заметки релиза | куда попадает отобранное в выпуск | скилл выпуска |
| Отобрано в релиз | состав, тексты которого утверждены | скилл выпуска |

Первые четыре нужны всем. **Последние два — только тем, кто выпускает версии**; в форме
у них есть вариант «не используется», и по умолчанию они пусты.

Пример конфига для флоу с ревью, стендом и релизом:

```json
{
  "pipeline": ["backlog", "todo", "to_fix", "development",
               "review", "to_testing", "testing", "ready_to_deploy", "done", "cancelled"],
  "actions": { "create": "backlog", "pick": "todo",
               "start": "development", "return": "to_fix" }
}
```

Свой статус, которого нет в наборе, тоже можно завести — достаточно описать оформление:

```json
"statuses": { "hotfix_wait": { "label": "Ждёт окна", "section": "Hotfix Wait", "color": "rose" } }
```

## Правила движения

Пайплайн описывает **ожидаемый** маршрут, а не забор. Простую задачу можно
двинуть из разработки сразу в тестирование, а ночной хотфикс — сразу в завершённые.
Ближайший следующий статус скиллы и UI предлагают первым, остальные доступны без церемоний.

**Запретов нет, пока этап ничего не требует.** Объявив требование этапа (Настройки ⚙ →
«Жизненный цикл», кнопка `✓` у статуса), вы делаете его условием выхода: агент не
уведёт задачу дальше, пока условие не выполнено или не списано явной командой. На
вас это не распространяется — карточки мышью переносятся как раньше, только доска
предупредит: что задача уедет с долгом, а при переносе в последний статус — что
требования так и останутся невыполненными. Подробнее — [«Доска, очередь и
задачи»](02-board.md).

Граница обещания: механизм **не** гарантирует, что этап выполнен, — он гарантирует,
что этап нельзя пройти молча. Пропуск перестаёт быть умолчанием и становится
отдельным поступком, у которого есть след в задаче.
Мягкое ограничение для мыши на доске (чтобы карточка не уехала случайным
движением) регулируется галкой «DnD по всей доске» (Настройки ⚙ → Жизненный цикл) — по умолчанию
она включена, и ограничения нет.

Два статуса ведут себя особо:

- **`cancelled`** — вне маршрута: перевести в него можно из любого статуса, но как
  «следующий шаг» он не предлагается никогда
- **`to_fix`** — статус возврата, поэтому стоит левее разработки: попадание в него из
  тестирования читается как движение назад, а «вперёд» из тестирования ведёт к релизу

## Кто занимается задачей на этапе

Кнопка **«исполнитель»** у статуса (там же, **Настройки ⚙ → «Жизненный цикл»**)
говорит, что этап спрашивает, кто занимается задачей. Из поставки не отмечен ни
один этап: отметьте те, где работу делает кто-то другой, — обычно это ревью и
тестирование. Нажатие снимает и ставит отметку, набор запоминается в проекте.

Что даёт отметка:

- в открытой задаче появляется метка исполнителя, которой назначают человека
  (см. [«Доска»](02-board.md));
- **агент не переведёт задачу на такой этап без имени** — скрипт откажет, и агент
  спросит у вас, кого назначить;
- **вас доска не гейтит**: перенести карточку можно всегда, но пока имени нет,
  задача стоит с долгом «исполнитель назначен» — он виден на карточке ⚠ и в
  вопросе перед переносом.

На неотмеченном этапе назначить исполнителя нельзя — ни в окне задачи, ни через
API, ни скриптом. Снять назначение можно на любом этапе: задачу могли перенести
оттуда, где имя спрашивали.

Список имён общий для всех проектов машины: он пополняется тем, что вы вводите в
поле (или что передал агент), и хранится в `~/.taskboard/config.json`.

## Требования этапа

Настраиваются там же: **Настройки ⚙ → «Жизненный цикл»**, кнопка `✓` у статуса. Она
раскрывает список того, что должно быть выполнено, **чтобы уйти с этого этапа**.

- **Рекомендации** показаны сразу и помечены точкой. Это то, что уже подводило на
  практике: подтверждение проверки человеком, тексты релиза. Пока требование не
  сделано обязательным, агент получает о нём напоминание, но этап проходит.
- Кнопка **«Сделать обязательным»** превращает напоминание в условие выхода. Ничего
  больше настраивать не нужно — это и есть основной способ включить проверку.
- **Своё требование** добавляется формой ниже. Проверок четыре:

| Проверка | Что смотрит |
|---|---|
| подтверждение человека | вы нажали кнопку в диалоге переноса или сказали агенту |
| секция есть в файле задачи | заголовок на месте — важен лишь факт наличия секции |
| секция непуста | в секции есть хотя бы одна строка |
| поле задачи заполнено | например `epic` или ссылка на MR |

У каждого требования есть служебное имя (`verified`, `commits`): им оно
отмечается выполненным, и оно попадает в файл задачи. Формулировка — то, что
увидите вы и агент.

**Имя занято — требование не добавится.** Под одним именем это одно требование,
на каком бы этапе оно ни стояло: отметка закрыла бы оба этапа сразу, а
формулировки в списке при этом разные. Редактор скажет, чем имя занято, — и не
даст включить одноимённую рекомендацию. Совпадение, уже записанное в настройках
руками или приехавшее из другого проекта, назовут «Проблемы данных» на доске;
переименовать его за вас нельзя — имя уже стоит в файлах задач, и правка молча
обнулила бы их отметки.

### Кого требование не касается

У каждого требования в списке есть подпись типов: **«все типы»** или
**«кроме: …»**. Нажмите её — и отметьте типы задач, к которым требование
не относится; отметки снимаются тем же нажатием. Задать это можно и сразу
при создании требования, строкой «Не касается задач».

Так снимаются требования, бессмысленные по смыслу работы: у задачи-обсуждения
секция «История коммитов» пуста не по недосмотру — коммитов по ней не будет
никогда. У задачи исключённого типа требование не спросят ни с агента, ни
значком долга на карточке.

Рекомендации поставки приходят со своими исключениями — их видно в списке до
включения.

**Поставка может уйти вперёд.** Ваши требования сохраняются в настройках проекта
в тот момент, когда вы добавляете статус, и дальше живут отдельно. Появится в
инструменте новый тип задачи, для которого требование снято, — ваш снимок об
этом не узнает, и задача такого типа упрётся в отказ, закрыть который нечем.

Такое расхождение видно в баннере: он называет требования и типы поимённо, а
кнопка **«Дописать»** добавляет недостающие типы в исключения. Именно
**дописывает**: формулировки, предикаты и ваши собственные исключения остаются
как были — требования принадлежат вам, а не поставке.

**Ваши собственные требования инструмент не правит.** Если требование придумали
вы, относится оно к новому типу или нет — знаете только вы. Про такие баннер
не чинит, а **спрашивает**: называет тип и предлагает «Настроить» — кнопка
открывает настройки жизненного цикла. Вопрос задаётся **один раз**: решите вы
добавить исключение или оставить как есть, второй раз про этот тип не спросят.

Ничего не сделать тоже можно: задача нового типа тогда упрётся в требование —
и вы настроите его в тот момент, когда это действительно понадобится.

**Включение показывает цену.** Требование действует и для задач, которые прошли
этап раньше: перед сохранением доска перечислит их и спросит, включать ли. Отменить
можно там же.

Что уместно требовать и как долг выглядит на доске —
в [«Доска, очередь и задачи»](02-board.md).

## Что происходит при изменении пайплайна

- включили статус — раздел появляется в `board.md` на своём месте по порядку;
- выключили пустой — раздел убирается;
- выключили статус с требованиями — они убираются вместе с ним: остаться они могли бы
  только мёртвым блоком в настройках;
- выключили статус с задачами — UI спросит, куда их перенести, и подвинет и строки доски,
  и `status:` во frontmatter файлов задач;
- секция правил в `AGENTS.md` / `CLAUDE.md` пересобирается под новый маршрут.

## Смена статуса вручную и агентами

```sh
# py — лаунчер Windows; нет его (Python из Microsoft Store) — зовите python,
# на macOS/Linux — python3
py tasks/set_status.py TASK-004 development --agent "Имя (модель)"
python tasks/set_status.py TASK-004 development --agent "Имя (модель)"
py tasks/set_status.py --list              # пайплайн проекта
py tasks/set_status.py TASK-004 --targets  # куда можно двинуть задачу
py tasks/set_status.py TASK-004 --debt     # чем задача должна этапам
py tasks/set_status.py --queue             # очередь прямо сейчас (--limit 0 — вся)
py tasks/set_status.py --changelog         # состав выпуска и его тексты
py tasks/set_status.py TASK-004 --note "суть" --agent "Имя (модель)"  # комментарий
```

Скрипт правит `status:` в файле задачи и строку в `board.md` за один вызов — руками
их лучше не разводить. Он же пишет комментарии (`--note`): время берёт из системы,
строку ставит в конец раздела «Комментарии» — подробнее в разделе «Структура». Скиллы (`start-task`, `fix-task`, `finalize-task`) имён статусов
не содержат: они спрашивают их у скрипта, поэтому подстраиваются под пайплайн проекта сами.

`--queue` отвечает на вопрос «что брать следующим»: раздел очереди в порядке
следования, каким он стал **сейчас**. Агенту это важнее, чем вам: пока он работал
над задачей, вы могли переставить приоритеты на доске, и очередь, названная
по памяти сессии, оказалась бы устаревшей. Правила требуют спрашивать её этой
командой, а не пересказывать прочитанное в начале работы.

`--changelog` отвечает на вопрос «что и какими словами едет в выпуск»: задачи
утверждённого состава в порядке доски, у каждой — текст из её секции «Изменение
для пользователя». Три ответа различаются намеренно: текст, пустая строка
(«пользователю сказать нечего» — решение принято) и `null` (секции нет вовсе,
до задачи не добирались). Этим режимом скилл выпуска и собирает changelog,
вместо того чтобы вычитывать файлы задач по одному. Нужен другой статус —
`--changelog <статус>`.

## Когда работа над задачей кончается

С релизным хвостом последний статус наступает не тогда, когда исполнитель
закончил: задача уходит в пул готового и ждёт выпуска, а закрывает её уже релизный
скилл — днями позже и в другой сессии. Поэтому то, что делается «в конце», делается
**раньше**, и у этого «раньше» две разные точки.

**Первая — когда задача уходит на проверку**, то есть покидает рабочий статус.
Здесь агент сохраняет знание о проекте в волт. Почему не позже: следующий шаг
может случиться без него — вы перенесёте карточку мышью, и записывать знание будет
уже некому. Об этом напоминает та же команда смены статуса:

```
[!] работа над задачей кончилась — что выяснилось про проект, сохраните в волт …
```

**Вторая — когда работа по задаче закончена**, обычно сразу после того, как вы
подтвердили проверку. Момент вычисляется по вашему маршруту, а не по имени статуса:

- **есть статус подготовки текстов релиза** — работа кончается в статусе перед ним;
- **нет** — работа кончается в последнем статусе маршрута.

Здесь агент дозаполняет файл задачи:

```
[!] незакрытых пунктов плана: 2 — «Написать тест», «Обновить справку»
[!] секция «История коммитов» пуста: по строке на коммит задачи …
[!] задачу ждут: TASK-039 — их пометки снимают у них: --unblock TASK-041
```

Про коммиты не напомнят задачам, у которых их не бывает, — обсуждению и
код-ревью: там пустая секция это норма, а не долг.

Почему точки разные: план работы и коммиты **раньше закрыть нельзя** — план
кончается вместе с работой, а коммит во многих процессах идёт после вашей
проверки. Знание наоборот **нельзя откладывать**: до второй точки задача может
доехать и без агента — вашей рукой на доске.

Проверяемое скрипт проверяет сам, поэтому называет конкретные пункты, а не общую
фразу. Про волт он может только напомнить — стоит ли сохранять знание, решает
человек; тем, у кого волта нет, про него и не говорится.

Это подсказка, а не запрет: переход выполняется в любом случае.
