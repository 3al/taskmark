# Выпуск версий

Раздел нужен, если вы **выпускаете свой проект версиями**: собираете набор
готовых задач, пишете, что изменилось, и отдаёте пользователям. Если задачи
просто закрываются по одной — этот раздел можно пропустить, ничего настраивать
не придётся.

Не путайте с [«Обновления и версия»](07-updates.md): там про то, как **вы
получаете** новые версии Taskmark, здесь — как **вы выпускаете** свой проект.

## Почему этапов выпуска два, а не один

Проверенных задач копятся десятки, и в ближайший выпуск едут не все: состав
**выбирается**. Поэтому в наборе статусов есть три подряд, и каждый отвечает
на свой вопрос:

| Статус | Что означает |
|---|---|
| **Готово к выпуску** | проверено, может поехать. Пул, задача ждёт здесь сколько угодно |
| **Заметки о релизе** | отобрано в готовящийся выпуск, пишется текст изменения |
| **В ближайший релиз** | текст вычитан и утверждён, задача точно едет |

Готовый маршрут с ними — пресет **«С релизами»** в Настройках (⚙) → Жизненный
цикл. Можно и вручную: добавить статусы и назначить действия **«Готовить заметки
релиза»** и **«Отобрано в релиз»** — по ним скилл понимает, куда переносить.

Отдельно в наборе есть **«К деплою»**: выкатка на стенд или прод — другой
процесс, а не выпуск версии. Обычно в маршруте нужен либо тот, либо другой.

## Как проходит выпуск

Скажите агенту **«готовь релиз»** — дальше по шагам:

1. Показывает все три релизные колонки — пул готового и то, что уже лежит
   в «Заметках о релизе» и «В ближайшем релизе», — и спрашивает, что добавить
   из пула.
2. Переносит отобранное в «Заметки о релизе» и пишет **текст для пользователей**
   в каждой задаче, у которой его ещё нет, — в секцию «Изменение для пользователя».
3. Показывает черновики. Вы правите формулировки или убираете задачу из выпуска.
4. Переносит утверждённое в «В ближайший релиз» и собирает changelog по тому,
   что в этой колонке лежит.
5. Предлагает разряд версии с обоснованием и, после подтверждения, выпускает.

**Три решения остаются за вами**: состав выпуска, формулировки для пользователей
и разряд версии. Всё между ними делается без вашего участия.

### Задачу можно положить в релиз мышью

Перетащить карточку сразу в «Заметки о релизе» или «В ближайший релиз» — обычный
способ работы, а не обход порядка: доска источник правды. Скилл такие задачи
подхватывает наравне с отобранными им самим: напишет недостающий текст, включит
в changelog и закроет после выпуска.

Единственное, о чём он предупредит, — задача, лежащая в «В ближайшем релизе»
**без текста**. Колонка утверждённого выглядит одобренной, поэтому такую задачу
он не пропустит молча: назовёт её и предложит написать текст до выпуска.

### Почему тексты пишутся заново

Заголовок задачи написан для того, кто с ней работал: «Починка односторонних
блокировок кнопкой» человеку, решающему обновляться ли, не говорит ничего.
В changelog нужен результат — «блокировки между задачами больше не расходятся».
Поэтому скилл пишет черновик заново, а не копирует заголовки.

Текст можно **поправить прямо в карточке задачи** — у секции «Изменение для
пользователя» есть карандаш, как у описания и критериев.

**Если сказать нечего — оставьте пусто.** Рефакторинг, тесты, правки внутренней
механики пользователь не заметит, и строка «Исправление багов» ему ничего не даёт:
она занимает место и заставляет гадать. Пустая секция — обычный исход, задача
просто не попадёт в текст выпуска.

**Одинаковые тексты объединяются.** Несколько задач могут дать один и тот же
результат для пользователя — в changelog он попадёт одной строкой. Объединяются
только полностью совпадающие формулировки; похожие остаются как есть, чтобы
машина не решала за вас, одно это изменение или разные.

## Свой скрипт выпуска

Дальше подготовки Taskmark не идёт: «выпустить» у каждого значит своё — собрать
артефакт, поднять версию в `package.json`, дёрнуть CI, выкатить на сервер.

**Если скрипт не подключён**, скилл доводит подготовку до конца и останавливается:
состав отобран, тексты написаны, changelog собран. Выпускаете вы, как принято
в проекте, и переводите задачи в терминальный статус.

**Если подключён** — скилл вызовет его сам и закроет задачи после успеха.

### Как подключить

Положите скрипт куда удобно **внутри проекта** и укажите путь в Настройки (⚙) →
**«Скрипт выпуска версии»**. Пустое поле — нормальное состояние: значит своего
механизма нет.

Путь хранится в `tasks/.taskboard.json` ключом `release_script`, поэтому его можно
задать и файлом:

```json
{ "release_script": "tools/release.py" }
```

Обратите внимание: настройка хранит **путь**, а не сам скрипт. Он часть вашего
проекта — лежит в репозитории, версионируется вместе с кодом и доезжает до всех,
кто с проектом работает. Поле рядом со «Скриптом создания задач» и «Скриптом смены
статуса» его не заменяет: те два — имена файлов, которые Taskmark разворачивает сам,
и переименование там тянет за собой перенос данных.

### Что скрипт получает и что должен вернуть

Аргументы на вход, JSON в стандартный вывод — как у `set_status.py --queue`.

**Проверка готовности.** Вызывается до вопросов пользователю, ничего менять
не должна:

```
<скрипт> --check --bump minor
```

```json
{ "ok": true, "current": "1.0.0", "next": "1.1.0", "blockers": [] }
```

`blockers` — список человекочитаемых причин, по которым выпустить нельзя прямо
сейчас: незакоммиченные правки, устаревшая сборка, что угодно ещё. Скилл покажет
их пользователю **списком целиком**, а не первую попавшуюся: чинить по одной,
каждый раз запуская выпуск заново, — худший из возможных сценариев.

**Выпуск:**

```
<скрипт> --apply --bump minor --notes путь/к/файлу --tasks TASK-001,TASK-002
```

```json
{ "ok": true, "version": "1.1.0", "tag": "v1.1.0" }
```

`--notes` — файл с телом секции changelog (без заголовка версии: его ставит сам
скрипт). `--tasks` — состав выпуска, если он вам нужен для сообщения коммита или
привязки.

**Публикация** — отдельным вызовом, потому что необратима:

```
<скрипт> --publish
```

Если после публикации нужно ещё что-то — например, создать запись о релизе
на хостинге, — делайте это там же и **не считайте провалом выпуска**: версия
уже выпущена. Отдельно сообщите, что именно не удалось.

```json
{ "ok": true, "pushed": true, "release": { "ok": false, "reason": "…" } }
```

**Отказ** — ненулевой код возврата и `{"ok": false, "error": "..."}`. Скилл
покажет текст ошибки и остановится, ничего не трогая дальше.

Разряд версии и тексты приходят снаружи намеренно: это решения человека,
а не свойство коммитов. Всё остальное — нумерация, сборка, теги, публикация —
дело вашего скрипта, потому что у каждого проекта своё.
