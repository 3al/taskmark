# Агентское окружение и среды

Что разворачивается в проект, зависит от выбранных сред. Выбор спрашивается при
первом открытии проекта и меняется в **Настройки (⚙) → Агенты**.

| Среда | Скиллы | Команды | Правила | Хуки |
|---|---|---|---|---|
| Claude Code | `.claude/skills/` | — | `CLAUDE.md` | `.claude/hooks/`, подключение в `.claude/settings.json` |
| opencode | `.opencode/skills/`, если нет Claude Code | `.opencode/commands/` | `AGENTS.md` | `.opencode/plugin/` |
| Codex | `.codex/skills/` | — | `AGENTS.md` | `.codex/hooks/`, подключение в `.codex/hooks.json` |

- Claude Code и opencode вместе держат скиллы одной копией в `.claude/skills/`.
  С Codex появляется вторая копия в `.codex/skills/`.
- `AGENTS.md` общий для opencode и Codex, поэтому при первом открытии предлагаются
  обе среды — лишнюю снимите.
- Хуки описаны ниже, в разделе «Хуки»; при включённом волте добавляются `vault/SYS/`
  и скилл `write-vault`.
- `board.md`, `create_task.py`, `set_status.py`, `notify.py`, `epics.md`, `logs/`
  разворачиваются при любом выборе.
- Папки со скиллами, командами и хуками получают `.gitignore`. Если свой файл уже
  есть, в него дописывается недостающая строка.

> ⚠️ **Не запускайте `/init` в проекте с развёрнутым окружением.** Команда
> перезапишет `CLAUDE.md` / `AGENTS.md`, и правила работы с задачами пропадут.

## Скиллы

| Скилл | Что делает |
|---|---|
| `new-task` | создаёт задачу |
| `start-task` | берёт задачу в работу и собирает контекст |
| `handoff-task` | отдаёт готовую работу на проверку и говорит, что проверять |
| `fix-task` | возвращает задачу после замечаний и планирует доработки |
| `review-task` | ревьюит чужую работу и пишет замечания в задачу |
| `finalize-task` | двигает задачу дальше по маршруту и прибирает хвосты |
| `brainstorm` | несколько агентов параллельно предлагают варианты |
| `brainstorm-team` | то же, с диалогом агентов между собой |
| `release` | готовит выпуск (см. [«Выпуск версий»](08-release.md)) |
| `write-vault` | сохраняет знание в Knowledge Vault |
| `write-handoff` | записывает буфер перехода в новую сессию |
| `read-handoff` | восстанавливает контекст из буфера и очищает его |

- `/start-task --info` (или `--help`, `-h`, `?`) показывает, что скилл делает и
  какие аргументы принимает, ничего не выполняя.
- Аргументы позиционные: `/start-task TASK-089 обрати внимание на блокировки` —
  номер, затем свободный текст.
- Скиллы узнают статусы у `set_status.py` и подстраиваются под маршрут проекта.

**Моменты маршрута закреплены за скиллами.** Взятие в работу, передача на
проверку, возврат, продвижение и выпуск через `set_status.py` напрямую не
проходят: скрипт назовёт нужный скилл. Агент может двинуть задачу и вручную, с
причиной — такой переход подписан в задаче как ручной. Повторный вход в работу
задачи, которая уже уходила дальше, ведёт `fix-task`.

**Задачу, которая стоит, агент не берёт.** Если задача заблокирована или на паузе, он
пропустит её в очереди, назовёт причину и предложит следующую свободную. Если вы
настаиваете — возьмёт с `--force`. Задача, чей блокер уже закрыт, стоящей не
считается; пометку снимаете вы.

Блокировки и паузу агент ставит тем же скриптом, срез простоя — `set_status.py
--stalled` (см. [«Доска, очередь и задачи»](02-board.md)).

## Уведомления от агента

Агент вызывает `tasks/notify.py`, когда ему понадобились вы: работа отдана на
проверку, нужен ваш ответ или работа встала. Если вы только что написали и работа была
короткой, он не зовёт. Как выглядят уведомления — в
[«Доска, очередь и задачи»](02-board.md).

## Логи агента

Агент сохраняет лог в `tasks/logs/`, только если материал понадобится
перечитать: рассуждение, протокол брейншторма, диагностику.

- Кодировка UTF-8; рассуждения и отчёты — Markdown.
- Временный вывод команд в проекте не остаётся.
- Протоколы брейншторма — с суффиксом `-brainstorm-log.md` или
  `-brainstorm-team-log.md`.
- Лог — история работы; актуальное знание о проекте хранится в Knowledge Vault.

## Переход в новую сессию

Буфер `tasks/handoff.md` переносит контекст в новую сессию или другую среду:

- `write-handoff` записывает, с чего начать, что сделано по каждой задаче сессии
  и на какие грабли наступили;
- `read-handoff` читает буфер в начале следующей сессии и стирает его.

Статусы задач берутся из файлов в момент чтения. Буфер старше часа агент
покажет и спросит, восстанавливать ли. Если прежний буфер не забран, новая запись
не выполнится — агент спросит, что делать.

Вернуться в ту же сессию можно средствами среды: `claude --continue`,
`opencode -c`, `codex resume --last`, сжать контекст — `/compact`.

## Секция правил

Секция в `CLAUDE.md` / `AGENTS.md` описывает для агента работу с задачами. Она
лежит между маркерами:

```markdown
<!-- task_management:rules — секцию ведёт доска задач, текст вне маркеров не трогается -->
# 5. TASK MANAGEMENT
…
<!-- /task_management:rules -->
```

- Сверка и обновление касаются только текста между маркерами.
- Секция без маркеров узнаётся по заголовку `# … TASK MANAGEMENT`; маркеры
  появятся при первом обновлении.
- **Старая секция** — заголовок любого уровня вне маркеров, начинающийся с «Task
  Management» (можно с номером). Баннер «Рядом с правилами для агентов осталась
  старая секция Task Management» → «Подробности» → **«Удалить»** вырежет её с
  подразделами; текст сохранится в `tasks/.taskboard/backup/rules/`.
- Свои правила работы с задачами под другим названием не распознаются —
  согласуйте их с секцией сами.

## Хуки

Вместе с окружением разворачиваются обработчики хуков:

| Среда | Файл | Подключение |
|---|---|---|
| Claude Code | `.claude/hooks/work-hint.py` | `.claude/settings.json` |
| Claude Code | `.claude/hooks/attention-notify.py` | `PermissionRequest` и `Notification` в `.claude/settings.json` |
| opencode | `.opencode/plugin/work-hint.js` | подхватывается сам |
| opencode | `.opencode/plugin/attention-notify.js` | подхватывается сам |
| Codex | `.codex/hooks/work-hint.py` | `.codex/hooks.json` |
| Codex | `.codex/hooks/permission-notify.py` | `PermissionRequest` и `PreToolUse` (вопрос) в `.codex/hooks.json` |

**Подсказка при коммите** (`work-hint`). Коммит, `push` или запрос на слияние при
задаче в работе — агенту напоминают, что передачу ведёт скилл. Ничего не
блокируется. Отключить — удалить запись из `hooks.PostToolUse`; при следующем
развёртывании она вернётся, пока среда включена.

**Вызов человека** (`attention-notify`, `permission-notify`) — уведомление на
доске:

- **жёлтое «ждёт разрешения»** — среда показала диалог подтверждения;
- **голубое «ждёт вашего ответа: задан вопрос»** — агент задал вопрос с
  вариантами;
- **голубое «ждёт вашего ответа»** — терминал долго ждёт ввода (только Claude
  Code).

У Codex инструмент вопроса по умолчанию есть только в режиме Plan. В режиме
Default его включает экспериментальная функция:

```
codex features enable default_mode_request_user_input   # насовсем, в ~/.codex/config.toml
codex --enable default_mode_request_user_input          # только на этот запуск
```

В `codex exec` инструмента нет. Без него агент спрашивает обычной репликой, и
уведомления о вопросе не будет. Команды и параметры в уведомление не попадают.

Регистрация хука ставится в файл настроек среды, не трогая остальные записи. Нет
файла или записи — баннер, кнопка развёртывания восстанавливает оба.

### Хуки в Codex

- Проект должен быть **доверенным**, иначе Codex не читает `.codex/hooks.json`.
- При старте сессии Codex показывает «Hooks need review» — хуки нужно одобрить.
  После обновления поставки он спросит снова.
- Хуки читаются при старте: после развёртывания или обновления перезапустите
  сессию. Проверить — командой `/hooks`.

## Ревью чужой работы

Скилл `review-task` разбирает чужое изменение и записывает замечания в задачу
типа «Код-ревью».

- **Предмет** — ключ задачи (ищется в коммитах), хэш коммита или ветка. Задачи нет
  — скилл её заведёт.
- **Результат** — секция «Замечания ревью»: блокирующие отдельно от
  необязательных, у каждого — место, суть и источник.
- **Правила** берутся в порядке приоритета: `CODE_REVIEW.md` в корне, конфиги
  анализаторов, `CLAUDE.md` / `AGENTS.md`, Knowledge Vault, кодовая база, общие
  практики. После первого ревью скилл предложит создать `CODE_REVIEW.md`.
- **Анализаторы** запускаются после вашего разрешения. Зависимости скилл не
  ставит и автоправку не включает.

**Настройки (⚙) → Агенты → Внешние источники ревью** — предметом может быть merge
request. Он берётся через MCP-инструменты вашей среды. Замечания отправляются в
MR только после вашего подтверждения, по одному комментарию; состояние MR скилл
не меняет. Выключено — `review-task` и `fix-task` работают только с локальными
данными.

## Knowledge Vault

> **Волт — база знаний о проекте в его текущем состоянии**: как устроен код, какие
> в нём правила и почему он сделан так. Это не лог работы и не история
> доработок: в заметках нет ссылок на задачи и рассказов «сначала сделали X,
> потом переделали». Устарело — заметку обновляют, а не дописывают.

Агент читает волт при старте задачи, чтобы не изучать код заново, и пополняет,
отдавая работу на проверку. Включается галочкой при развёртывании или
в **Настройки (⚙) → Агенты → Knowledge Vault**.

| Что | Зачем |
|---|---|
| `vault/SYS/structure.md` | правила ведения заметок |
| `vault/SYS/templates/` | шаблоны заметок `business` и `code` |
| `vault/SYS/taxonomy.md` | теги — заполняете вы |
| `vault/SYS/README.md` | вводная |
| скилл `write-vault` | создание и обновление заметок |
| блоки про волт | в скиллах и правилах |

- Заметки лежат в `vault/<домен>/`; для новой возможности пишется пара
  `business` + `code`.
- Папка `vault/` не попадает в git. Обычный поиск её не видит — используйте явные
  пути или `rg --no-ignore "<слово>" vault/`.
- `structure.md` и шаблоны сверяются с поставкой; `README.md`, `taxonomy.md` и
  заметки — ваши.
- **Выключили волт** — блоки про него уйдут из скиллов при обновлении, а
  `write-vault` попадёт в баннер как лишний: «Подробности» → **«Удалить»**
  (копия — в `tasks/.taskboard/backup/`). Папка `vault/` не удаляется.

## Обновление и правки

Баннер показывает, чего не хватает и что отстало от шаблона. Части невыбранных
сред не проверяются, ваши собственные скиллы не трогаются.

**Развёртывание не перезаписывает файлы.** Разошедшийся с шаблоном файл остаётся
как есть и приводится к шаблону только кнопкой в окне расхождений.

Taskmark хранит копию развёрнутого — `tasks/.taskboard/baseline/`. Пока шаблон не
менялся, ваши правки баннер не вызывают.

Кнопка **«Подробности»** открывает окно расхождений:

| Состояние | Что значит | Кнопки |
|---|---|---|
| отстал от шаблона | вы не правили, шаблон обновился | «Обновить» |
| правки в проекте, шаблон обновился | изменились обе стороны | «Слить», «Взять шаблон», «Оставить свою» |
| происхождение неизвестно | нет сохранённой копии | «Взять шаблон», «Оставить свою», иногда «Слить» |
| не развёрнут | файла нет | «Развернуть» |

- **Слить** — ваши правки сохраняются, изменения шаблона добавляются. Конфликты
  остаются в файле маркерами `<<<<<<<`. Нужен git.
- **Взять шаблон** — файл приводится к шаблону.
- **Оставить свою** — файл не меняется до следующего обновления шаблона.
- **«Обновить безопасные (N)»** — только файлы без ваших правок.
- **«Слить все (N)»** — всё, что сливается; файлы с конфликтами будут перечислены.

Перед перезаписью прежний файл сохраняется в
`tasks/.taskboard/backup/<часть>/<имя>` (последняя копия).

**Происхождение неизвестно.** Taskmark ищет похожую версию шаблона в своей
истории git и показывает процент совпадения:

- точное совпадение — файл считается «отстал от шаблона»;
- от 20% — доступно «Слить»; ниже 70% — предупреждение о множестве конфликтов;
- ниже 20% или Taskmark установлен архивом — только «Взять шаблон» и «Оставить
  свою».

К секции правил это не относится.
