# Структура tasks/

Всё, чем живёт доска, лежит в папке `tasks/` вашего проекта:

```
tasks/
  board.md            # доска: разделы-статусы и строки задач
  TASK-001-*.md       # файлы задач
  _TEMPLATE.md        # эталон структуры задачи (по нему создаются новые)
  epics.md            # реестр эпиков: ключ → имя
  create_task.py      # создание задачи (номер, файл, строка на доске)
  set_status.py       # смена статуса (frontmatter + board.md за один вызов)
  logs/               # логи работы (показываются кнопкой «Логи»)
  .taskboard.json     # настройки проекта: жизненный цикл задач
  .gitignore          # папка не попадает в репозиторий проекта
```

Имена фиксированы: `board.md`, `create_task.py`, `set_status.py` и папка логов
называются одинаково во всех проектах.

Скиллы и правила для агентов лежат вне `tasks/` — см.
[«Агентское окружение и среды»](05-agentic.md).

## board.md

Доска — источник правды о том, где какая задача. Разделы `##` — статусы (колонки),
подразделы `###` внутри — группы, строки — задачи. Рубрики бэклога на свежей
доске — это типы задач («Новый функционал», «Баги», «Рефакторинг», «Уборка»,
«Обсуждения», «Дизайн», «Код-ревью»), и новая задача ложится в рубрику своего
типа. Рубрики
можно переименовать или завести свои — тогда задача просто добавится в конец
раздела приёма:

```markdown
## To Do

- TASK-042 · [Поиск по доске](TASK-042-поиск-по-доске.md) · Claude Opus 5 · 2026-07-28
```

В строке: номер, ссылка на файл задачи, кто последним менял статус и когда.
Раздел `## Потерянные` — технический: туда [починка данных](06-validation.md)
складывает записи, у которых не осталось файла задачи; колонкой он не показывается.
Заголовок внутри `[…]` — обычный текст: квадратные скобки в нём (`[BE] [VIEWER]
Счетчик посылок`) допустимы и доску не ломают.

## Файл задачи

```markdown
---
id: TASK-042
title: Поиск по доске
epic: ~
type: feature
status: todo
created: 2026-07-28
---

## Описание            ← что и зачем, внутри «### Критерии приёмки»
## Комментарии         ← лог для следующей сессии
## История коммитов    ← все коммиты по задаче
```

Структуру задаёт **`tasks/_TEMPLATE.md`** — эталон, который лежит рядом с задачами:
его копируют при ручном создании, по нему же `create_task.py` собирает новую задачу.
Хотите другие разделы — правьте шаблон, новые задачи пойдут по нему.
Кнопка «Обновить» на баннере вернёт шаблон к поставляемому виду.

**Комментарии — каждый отдельной строкой списка:**

```markdown
- **2026-07-28 14:32** · Claude Opus 5 · причина бага в парсере доски, правим регулярку
```

Так они не склеиваются: соседние строки без дефиса markdown собирает в один абзац,
из-за чего лог превращается в нечитаемое полотно. В строке — дата со **временем**
(видно порядок событий внутри дня), модель агента и суть.

Строку пишет не агент руками, а скрипт — `set_status.py TASK-NNN --note "суть"
--agent "модель"`. Время он ставит **системное**, а строку добавляет **в конец**
раздела, поэтому лог остаётся хронологией: старые записи сверху, свежие снизу.

**Переводы статуса пишутся сюда же — сами.** Каждая смена статуса добавляет строку
с тем, откуда и куда уехала задача:

```markdown
- **2026-07-28 15:04** · доска · Development → Testing
- **2026-07-28 18:20** · скрипт (Claude Opus 5) · Testing → Ready for Release
```

В окне задачи такая строка отличается от обычного комментария с одного взгляда:
маркер списка заменён отбивкой слева, а названия статусов окрашены цветами своих
колонок.

Подпись строки — **источник перехода**: `доска` — карточку перенесли мышью,
`скрипт (модель)` — задачу двигал агент через `set_status.py`. По истории видно
не только когда задача меняла этапы, но и сколько раз возвращалась и прошёл ли
переход через инструмент.

Возврат назад даёт **две строки**: сам перевод и снятое подтверждение, если оно
было — это разные факты об одном событии.

**Так же сами пишутся и остальные действия по задаче** — блокировка и пауза,
смена типа, переименование:

```markdown
- **2026-07-29 10:12** · доска · блокировка: ждёт TASK-013
- **2026-07-29 10:12** · доска · пауза: ждём ответ контрагента
- **2026-07-30 09:40** · скрипт (Claude Opus 5) · тип: bug (было feature)
- **2026-07-30 11:05** · доска · название: «Новое» (было «Старое»)
```

Блокировка записывается **обоим концам**: ждущая задача получает строку
«блокировка: ждёт TASK-013», блокирующая — «блокирует TASK-014». Снятие
пишется так же, и переезд в конец маршрута, снимающий простой сам, тоже
оставляет след.

Смысл в том, что файл задачи, прочитанный сверху вниз, даёт полную картину:
frontmatter показывает только нынешнее состояние, а не то, когда и что с
задачей сделали.

**Заголовки разделов — структура файла.** Их не переименовывают и не переставляют,
а «История коммитов» остаётся последней. При каждой смене статуса скрипт проверяет
файл и печатает `[!] …`, если раздел пропал или задвоился, разделы разъехались либо
комментарии идут не по времени.

Служебные пометки в файле — комментарии вида `<!-- ... -->` — на доске не показываются
и не попадают в копирование задачи: они остаются в файле для агентов, но чтению не мешают.

**Абзацы.** Markdown склеивает соседние строки в один абзац — новый начинается после
пустой строки. Это правило одно для всех путей: и когда вы правите файл руками, и
когда пишете описание в форме создания. Текст сохраняется как есть, поэтому перенос
внутри абзаца остаётся переносом исходника, а новый абзац начинается с пустой строки;
перечисления пишите списком. Правила поставки требуют того же и от агентов, чтобы
описания не превращались в простыню.

Статус хранится в двух местах — `status:` во frontmatter и раздел `board.md`.
Разводить их руками не нужно: перетаскивание на доске и `set_status.py` правят оба.

**Тип задачи** — поле `type:`: `feature`, `bug`, `refactor`, `cleanup`,
`discussion` (обсуждение, а не код), `design` или `review` (разбор чужого кода).
Он выбирается при создании,
рисует метку на доске и задаёт подраздел бэклога (см.
[«Создание задачи»](02-board.md)). Сменить тип позже — кликом по метке в открытой
задаче или командой `set_status.py TASK-NNN --type bug`; полный список —
`set_status.py --types`. Задачи, заведённые до появления поля, типа не имеют —
у них метка пустая, и тип ставится тем же кликом.

**Размер задачи** — поле `size:`: `S`, `M`, `L` или `XL`. Он отвечает на другой
вопрос, чем тип: не «что это за работа», а «сколько тут работы». Размер виден
буквами на карточке, и по нему на доске отбирают задачи (см.
[«Доска»](02-board.md)).

Оценку ставит агент, когда берёт задачу в работу и уже изучил контекст: при
заведении её строить не на чем. Поменять или снять её можно в открытой задаче —
кликом по метке рядом с типом — либо командой `set_status.py TASK-NNN --size L`
(пустое значение снимает). Что означает каждая буква, скажет
`set_status.py --sizes`. Задача без размера — норма: оценки просто ещё не было.

**Исполнитель** — поле `assignee:`: кто занимается задачей **сейчас**. Его
спрашивают не на каждом этапе, а только там, где вы поставили галочку
«исполнитель» (см. [«Жизненный цикл»](04-lifecycle.md)); из поставки не отмечен
ни один этап.

Ставится и снимается в открытой задаче, кликом по метке рядом с типом и
размером; список имён общий для всех проектов машины и пополняется по ходу —
новое имя запоминается, как только вы его назначили. Агент назначает тем же
скриптом: `set_status.py TASK-NNN testing --assignee "Иванов"`, а известные
имена спрашивает командой `set_status.py --assignees`.

На этапе, который спрашивает исполнителя, пустое поле — долг: агент не уведёт
задачу дальше и не переведёт её туда, пока имени нет.

Тип задаёт ещё и **подсказку следующего шага**. У обсуждений и код-ревью нет
релизного хвоста: статусы «Ready for Release», «Release Notes», «To Release» и
«Ready to Deploy» агенту по таким задачам не предлагаются — после проверки идёт
закрытие. Это рекомендация, а не запрет: перетащить такую задачу в любой статус
маршрута по-прежнему можно.

## epics.md

Эпик — Jira-подобный ключ (`E056-18500`), объединяющий несколько задач. Имя эпика
хранится только в `epics.md`; в задаче стоит лишь ключ в поле `epic:`. Состав эпика
показывает скрипт — с номером, статусом и заголовком каждой задачи, в порядке
маршрута:

```sh
set_status.py --epic E056-18500
```

Ключ с опечаткой не даёт пустой список: скрипт скажет, что такого эпика нет, и
перечислит те, что есть в реестре.

Из доски то же самое показывает окно эпика — клик по ключу на карточке или в
открытой задаче (см. раздел «Доска»).

## Настройки проекта

`tasks/.taskboard.json` — жизненный цикл статусов, выбранные среды
агентов. Файл лежит внутри `tasks/`, потому что папка игнорируется git: настройки не
засоряют репозиторий проекта, но переезжают вместе с ним.

Скрипты `tasks/*.py` автономны — они читают этот конфиг сами, рядом с собой, и
работают без запущенного сервера доски.

## Настройки инструмента

Свойства самого Taskmark — порт, тема, режим проверки обновлений — лежат отдельно,
в `~/.taskboard/config.json`: они ваши, а не репозитория, и одни на все проекты.
Рядом там же `projects.json` — список подключённых проектов.

**В файле хранится только то, что вы меняли.** Остальное берётся из поставки,
поэтому новые версии могут поправить значение по умолчанию — и оно у вас применится.
Записанное вами так не перезаписывается: ваш выбор всегда сильнее.

Отсюда и вид файла: у нового пользователя он пустой (`{}`), и это нормально —
работает всё на значениях по умолчанию. Вернули настройку к исходному значению —
ключ из файла исчезает и снова начинает следовать за поставкой.
