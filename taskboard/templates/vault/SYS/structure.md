# Структура заметок

## Фронтматтер

Каждая заметка ОБЯЗАТЕЛЬНО содержит YAML frontmatter:

```yaml
---
title:      # Человекочитаемый заголовок
created:    # YYYY-MM-DD
updated:    # YYYY-MM-DD
tags:       # Массив тегов из taxonomy.md
domain:     # Домен (system / домен проекта)
note-type:  # Тип: system / business / code
concept:    # (только для code) ссылка на business-заметку [[...]]
impl:       # (только для business) ссылка на code-заметку [[...]]
---
```

## Именование

- Файл: `kebab-case-latin-short.md`
- Папки: по доменам, одна папка на домен
- Запрещены: кириллица, пробелы, спецсимволы в именах файлов

## Содержание

### business-заметка

- **Что**: описание бизнес-концепции
- **Зачем**: мотивация, правила
- **impl**: ссылка на code-заметку

### code-заметка

- **Где**: файлы, классы, ключевые строки
- **Как**: поток данных, паттерн реализации
- **concept**: ссылка на business-заметку

## Чего в заметке быть не должно

Волт описывает **приложение**, а не работу над ним. Он самостоятельная сущность:
заметка обязана читаться без доступа к системе задач, к git и к переписке.

- **Номеров задач и тикетов.** Папка задач локальна и не в репозитории — ссылка
  на неё у следующего читателя не ведёт никуда, а заметку сдвигает в жанр отчёта.
- **Истории изменений** («сначала считали иначе, потом переделали»). Заметка
  говорит, как устроено **сейчас**. Отвергнутый вариант ценен — но описывается по
  сути: не «первая версия считала отрезок», а «считать отрезок нельзя: этап,
  пройденный мимо проверки, не проверялся бы уже никогда».
- **Метаинформации процесса**: кто делал, когда, каким скиллом, что подтверждено.
  Для этого есть файл задачи и история коммитов.
- **Пересказа кода.** Читать код проще, чем его пересказ; в заметке — где он
  лежит, как связан и почему сделан так.
- **Временных обходов** и планов на будущее: и то и другое устаревает молча, а
  верят им как знанию.

Признак, что заметка ушла не туда: её нельзя понять, не открыв задачу или
переписку. Значит знание в ней не записано, а только упомянуто.

## Обновление

- Не удаляй старые заметки — помечай `DEPRECATED` в начале
- Обновляй `updated` в frontmatter
- При изменении архитектуры — обновляй связанные code-заметки
- **Обновляй заметку на месте, а не дописывай «а теперь иначе»**: два состояния в
  одном тексте противоречат друг другу, и следующий читатель не знает, какое из
  них правда
