---
name: fix-task
description: >
   Вернуть завершённую задачу в работу после итерации ревью: найти задачу,
   восстановить контекст исходной реализации, собрать замечания ревью
   (из MR или в свободной форме), обсудить, составить план доработок.
   Используй когда пользователь говорит: "верни задачу", "возврат с ревью",
   "доработки по ревью", "review return", "fix task", "верни в разработку",
   "задача ушла на доработку", "переоткрыть задачу", "доработай задачу".
argument-hint: "<TASK-NNN | commit-hash>"
---

Верни задачу в разработку после ревью: контекст → замечания → план → доработки.

## Шаг 1. Определить задачу

Если аргумент передан (TASK-NNN) — использовать его.

Иначе:
1. Попробуй определить по контексту разговора (последняя упоминавшаяся TASK-NNN, ссылка на коммит, MR).
2. Если неясно — используй инструмент вопроса (Claude Code: `AskUserQuestion`; opencode: `question`):
   - Q: "Какую задачу вернуть в разработку?"
   - Предложи варианты из `tasks/board.md` (разделы Review, Testing, Completed)

Если аргумент — хэш коммита:
1. Выполни `git log --oneline -10` и `git show <hash> --stat` чтобы понять, к какой задаче относится коммит.
2. Ищи номер задачи (TASK-NNN) в сообщении коммита или связанных файлах.

Найди файл задачи: `glob` → `tasks/TASK-NNN-*.md`.

## Шаг 2. Прочитать текущее состояние

Прочитай `tasks/TASK-NNN-*.md` и `tasks/board.md`.

Узнай пайплайн проекта (имена статусов настраиваются per-project, по памяти их
подставлять нельзя): `py tasks/set_status.py --targets TASK-NNN`. Нужны
`actions.return` (куда возвращать) и `backward` (что задача уже прошла).

Обрати внимание на:
- `status` — задача должна быть уже за рабочим статусом (`actions.return`
  попадает в её `backward`): ревью, тестирование, релиз или завершение
- `patch: ~` или `patch: PATCH-NNN-Name` — если указан, знать какой патч был
- Описание, критерии приёмки, чеклист
- Раздел **«Заметки агента»** — восстановить контекст предыдущей работы
- Раздел **«История доработок»** — если есть записи, определи текущую итерацию

**Повторный возврат с ревью:** если статус уже равен `actions.return` И в разделе «История доработок» есть записи —
это новая итерация доработок по той же задаче (не первая). В этом случае:
- Продолжай работу с текущей итерации (шаг 3), не останавливайся
- Номер итерации = количество записей в разделе + 1
- Статус и board.md НЕ меняй — задача уже в работе

Если статус уже равен `actions.return` И раздел «История доработок» пустой — предупреди и уточни, нужен ли повторный сбор контекста.

## Шаг 3. Восстановить контекст исходной реализации

Посмотри, что было сделано в предыдущей итерации:

1. Прочитай заметки агента в файле задачи — они покажут ход работы, ключевые решения, блокеры.
2. Выполни `git log --oneline --all -- tasks/TASK-NNN-*.md` — найди коммиты, связанные с задачей.
3. `git show <commit> --stat` для каждого релевантного коммита — пойми, какие файлы менялись.
4. Прочитай ключевые файлы реализации (контроллеры, хендлеры, сущности, сервисы, тесты).
5. Если задача имеет `patch: PATCH-NNN-Name` — прочитай соответствующие файлы патча (если хранятся отдельно).

Сформулируй для себя: какие файлы были созданы/изменены, какая бизнес-логика зашита.

## Шаг 5. Вернуть задачу в работу

Целевой статус — `actions.return` из шага 2. Обычно это рабочий статус
(`development`), но проект может завести отдельный статус возврата (например
`to_fix`), и тогда скилл ведёт туда — имена в скилле не зашиты.

Статус меняй **скриптом** — он синхронно правит frontmatter и board.md
(переносит строку в раздел статуса первой, обновляет хвост `· АГЕНТ · дата`,
возвращает `_(нет)_` в опустевший раздел):

```
py tasks/set_status.py TASK-NNN <actions.return> --agent "<АГЕНТ>"     (Windows)
python3 tasks/set_status.py TASK-NNN <actions.return> --agent "<АГЕНТ>"
```

При **повторном возврате** (задача уже в этом статусе) скрипт просто обновит хвост
строки на новую дату — позиция не изменится, дублей не появится.

Если скрипта в проекте нет — правь вручную оба места (`status:` во frontmatter и
строку в разделе статуса возврата первой, `_(нет)_` в опустевшем разделе).

Затем в файле `tasks/TASK-NNN-*.md`:

1. Создай или дополни раздел **«История доработок»** (сразу после «Чеклист», перед «Заметки агента»).
   Если раздела ещё нет — добавь:
   ```
   ## История доработок

   <!-- Здесь фиксируются возвраты с ревью и последующие доработки -->

   ```
   Затем добавь запись о текущем возврате в начало раздела (самой свежей):
   ```
   ### Итерация N — возврат с ревью · YYYY-MM-DD

   **Источник:** MR !123 / свободная форма
   **Замечания:**
   - Замечание 1
   - Замечание 2
   **Что доработано:**
   - Описание изменений
   **Файлы:** `src/...`, `src/...`
   ```
   **Номер итерации N:**
   - Если записей ещё нет — первая итерация: `### Итерация 1 — возврат с ревью`
   - Если записи уже есть — последующая итерация: `### Итерация N — возврат с ревью`, где N = количество существующих записей + 1
   Поля **«Замечания»** и **«Что доработано»** заполняются на разных шагах:
   - Сейчас (шаг 5) — заполни **«Источник»** (позже будет известно из шага 6).
   - После сбора замечаний (шаг 6-7) — вернись и заполни **«Замечания»**.
   - После реализации (шаг 10) — вернись и заполни **«Что доработано»** и **«Файлы»**.

2. Добавь заметку агента в раздел «Заметки агента»:
   `<АГЕНТ>: YYYY-MM-DD: возврат с ревью (итерация N).`

## Шаг 6. Собрать замечания ревью

Используй **один** вызов инструмента вопроса (`AskUserQuestion` / `question`):

- header: "Источник замечаний"
- Q: "Откуда будем брать замечания ревью?"

Варианты:
1. **Ссылка на MR** — пользователь введёт URL merge/pull request
2. **Свободная форма** — пользователь опишет замечания вручную (через "Другой ответ")

### Если выбрана ссылка на MR:

1. Попроси пользователя ввести URL merge/pull request.
2. Если в проекте доступен способ прочитать MR (субагент, MCP-сервер, CLI вроде `glab`/`gh`) — извлеки все комментарии ревьюера, включая общие комментарии и inline-комментарии к коду (threads/discussions). Верни полный список: файл, строка, текст комментария.
3. Если способа прочитать MR нет — попроси пользователя вручную вставить замечания (свободная форма).

### Если выбрана свободная форма:

1. Попроси пользователя описать замечания (можно скопировать из GitLab/GitHub, мессенджера, email и т.д.).
2. Прими текст через ответ пользователя.

## Шаг 7. Заполнить замечания в истории

После того как замечания собраны и прояснены — вернись в файл задачи и заполни поле **«Замечания»** в записи «История доработок» (текущая итерация).
Отформатируй замечания в виде маркированного списка — кратко, по существу, с указанием файла, если применимо.

## Шаг 8. Анализ и обсуждение

Проанализируй замечания:
- Какие файлы требуется изменить
- Какая логика требует доработки
- Есть ли противоречия с исходными требованиями
- Нужны ли новые тесты

Если есть **сомнительные или неясные замечания** — используй инструмент вопроса для уточнения у пользователя:
- Q: "Замечание: {текст}. Как именно это должно работать?"
- Или: "Есть ли контекст/пример ожидаемого поведения?"

Не делай предположений — если неясно, спроси.

После уточнений — обнови поле **«Замечания»** в «Истории доработок», если формулировки изменились.

## Шаг 9. Представить план доработок

Когда все замечания ясны:

1. Составь краткий план: какие файлы меняются, что добавляется/убирается, какие тесты.
2. Покажи план пользователю через инструмент вопроса:
   - header: "План доработок"
   - Q: "Вот план доработок по замечаниям ревью. Приступаем?"
   - Варианты: "Да, приступай" / "Нет, нужно обсудить"

Если пользователь хочет обсудить — уточни и скорректируй план. Если утвердил — приступай к реализации.

## Шаг 10. Реализация доработок

Следуй стандартному workflow из правил проекта:
- **TDD** где применимо
- **Деструктивные операции с данными** (БД, файлы, продакшн-контуры) — только с подтверждения пользователя
- **Не коммить** без явного запроса
- **Если план расходится с обсуждённым** — остановись и согласуй
- В ходе работы добавляй компактные заметки агента в файл задачи

После завершения реализации — вернись в файл задачи и заполни поля **«Что доработано»** и **«Файлы»** в записи текущей итерации раздела «История доработок».
- **«Что доработано»** — краткое описание сути изменений («исправлена валидация статуса», «добавлена проверка прав доступа» и т.п.)
- **«Файлы»** — список изменённых файлов (относительные пути)

Также добавь заметку агента:
`<АГЕНТ>: YYYY-MM-DD: доработки по ревью завершены.`

## Шаг 11. Проверка после реализации

Обязательно:
- Запусти проверки проекта (линтеры, статический анализ, тесты — согласно правилам проекта).

Ручная проверка через HTTP/консоль/UI, если применимо.

Если проверки не проходят — исправь.

## Шаг 12. Локальная проверка

Попроси пользователя проверить результат:
- header: "Проверка"
- Q: "Доработки готовы. Можешь проверить?"
- Варианты: "Проверка прошла" / "Нужно исправить"

Если проверка не прошла — вернись к шагу 10.

## Завершение

Задача остаётся в статусе `development`. После одобрения следующего ревью
финализируй задачу скиллом `finalize-task`.

## Важно

- **Не редактируй чеклист задачи** — он остаётся как есть (доработки не меняют объём задачи)
- **Заметки агента**: добавляй новые строки, не удаляй старые — история важна для контекста
- **Повторные возвраты**: задача может вернуться с ревью несколько раз. Каждый вызов fix-task для уже работающей задачи (development + есть записи в «История доработок») — это новая итерация. Номер итерации в заголовке (`### Итерация N`) всегда указывай явно — это помогает отслеживать историю доработок.
- **Патч**: если после доработок меняется набор файлов — `patch` не обновляй, это responsibility finalize-task
- **При каждом коммите** по задаче: добавляй строку в секцию **«История коммитов»** файла задачи (если секции нет — создай в конце файла по образцу `tasks/_TEMPLATE.md`). Формат: `` - `<short-hash>` <сообщение коммита> ``, хронологически (свежие — в конец). См. правила проекта § «Правила работы с задачей».
- **Если коммитов по задаче нет** (задача доехала до конца пайплайна без реализации) — это не review-return, а start-task; сообщи пользователю и предложи использовать `start-task`
- **Чтение MR**: если способ прочитать MR недоступен — всегда падай на свободную форму, не блокируйся
