Проведи командный брейншторм реализации задачи через Agent Teams.

## Аргументы

Что скилл принимает — в `argument-hint` его заголовка. Аргументы **позиционные**:
первый имеет форму, остальное разбирается по описанию шагов.

**`--info`** (а также `--help`, `-h`, `?`) — покажи сигнатуру и ничего не выполняй:
что скилл делает, что принимает, два примера вызова, чего он делать не станет.

**Первый токен похож на флаг** (`--что-угодно`, `-x`, `?`), но это не `--info`, —
он не содержимое и не идентификатор. Покажи ту же сигнатуру и скажи, что такого
аргумента нет. **Не угадывай смысл**: именно так заводится задача с названием
`--help` и выпускается не та версия.

Первый токен подошёл — дальше всё как описано ниже, включая свободный текст.

## Шаг 0. Оценка целесообразности

После определения задачи и чтения файла задачи — оценить её размер:
- **S/M** (1-5 файлов) — **отказать**: "Задача S/M. Командный брейншторм избыточен (~6-7 вызовов агентов). Используйте `/brainstorm` вместо этого." Через инструмент вопроса пользователю (Claude Code: `AskUserQuestion`; opencode: `question`) с вариантами: "Переключиться на /brainstorm" / "Всё равно запустить team".
- **L** (5-10 файлов) — **предупредить**: "Задача L. Командный брейншторм может быть полезен, но `/brainstorm` дешевле (~3 вызова vs ~7). Продолжить?" Продолжить без переспроса.
- **XL** (10+ файлов, архитектурные развилки, несколько конкурирующих подходов) — запускать без предупреждений. Это целевой use case для `/brainstorm-team`.

## Шаг 1. Определить задачу

Если аргумент передан (TASK-NNN) — использовать его.
Иначе — спросить пользователя через инструмент вопроса (`AskUserQuestion` / `question`).

## Шаг 2. Прочитать контекст задачи

1. Найти файл задачи: `tasks/TASK-NNN-*.md` (через Glob)
2. Прочитать файл задачи целиком
3. Прочитать правила проекта (`CLAUDE.md` в Claude Code, `AGENTS.md` в opencode)
4. Если в задаче указаны конкретные файлы — прочитать их тоже

Сформировать **контекст** — краткое описание:
- Что нужно сделать (из описания задачи)
- Какие файлы затронуты
- Ключевые ограничения (из правил проекта)

## Шаг 3. Запустить команду агентов (Раунд 1 — исследование и предложения)

Запустить **три вызова субагентов параллельно в одном сообщении**, каждый с уникальным именем:

**opencode:** вместо `Agent` используй `task` с `subagent_type: "explore"` — три вызова в одном сообщении, промпты ролей бери из блоков ниже без изменений. Имён и `run_in_background` в opencode нет: **сохрани `task_id` из результата каждого вызова** — это дескрипторы ролей (architect / pragmatist / opponent), через которые ведутся последующие раунды. Модель не задаётся — все агенты на модели текущей сессии.

### Agent 1: Архитектор (opus)

```
Agent(
  name="architect",
  description="Архитектор: дизайн реализации",
  model="opus",
  run_in_background=true,
  prompt="""
Ты — Архитектор в команде из трёх экспертов.

## Задача
{контекст задачи}

## Твоя роль
- Предложить архитектурно правильное решение
- Фокус: паттерны, масштабируемость, тестируемость, SOLID
- Исследуй кодовую базу для обоснования

## Что сделать СЕЙЧАС
1. Исследуй кодовую базу (Read, Grep, Glob)
2. Сформулируй своё предложение в формате ниже
3. Верни результат — ведущий передаст его на критику

## Формат предложения
**Подход:** (1-2 предложения)
**Шаги:** (нумерованный список)
**Файлы:** (список с описанием изменений)
**Риски:** (что может пойти не так)
"""
)
```

### Agent 2: Прагматик (sonnet)

```
Agent(
  name="pragmatist",
  description="Прагматик: простая реализация",
  model="sonnet",
  run_in_background=true,
  prompt="""
Ты — Прагматик в команде из трёх экспертов.

## Задача
{контекст задачи}

## Твоя роль
- Предложить самый простой и быстрый способ реализации
- Фокус: минимум изменений, без over-engineering, практичность
- Исследуй кодовую базу для обоснования

## Что сделать СЕЙЧАС
1. Исследуй кодовую базу (Read, Grep, Glob)
2. Сформулируй своё предложение в формате ниже
3. Верни результат — ведущий передаст его на критику

## Формат предложения
**Подход:** (1-2 предложения)
**Шаги:** (нумерованный список)
**Файлы:** (список с описанием изменений)
**Что НЕ делать:** (осознанные упрощения)
"""
)
```

### Agent 3: Оппонент (sonnet)

```
Agent(
  name="opponent",
  description="Оппонент: исследование кодовой базы",
  model="sonnet",
  run_in_background=true,
  prompt="""
Ты — Оппонент (Devil's Advocate) в команде из трёх экспертов.

## Задача
{контекст задачи}

## Твоя роль
- Критически оценивать предложения других
- Находить слабые места, риски, пропущенные edge cases

## Что сделать СЕЙЧАС
1. Исследуй кодовую базу (Read, Grep, Glob) чтобы глубоко понять контекст задачи
2. Запиши свои наблюдения о потенциальных проблемах и edge cases
3. Верни результат — ведущий скоро пришлёт тебе предложения для критики

НЕ формулируй критику сейчас — только исследуй. Предложения придут позже.
"""
)
```

## Шаг 4. Модерировать дискуссию через SendMessage

**КРИТИЧЕСКИ ВАЖНО:** Ведущий (ты) — единственный координатор. Агенты НЕ общаются напрямую. Ты пересылаешь информацию между ними через `SendMessage`.

**opencode:** вместо `SendMessage(to="X", prompt=...)` во всех блоках ниже используй продолжение сессии субагента: `task(task_id: <task_id роли X>, prompt: ...)`. Механика та же: агент получает сообщение в своём накопленном контексте, его ответ возвращается тебе как результат вызова. Параллельные отправки (Раунд 3) — два `task`-вызова в одном сообщении.

### Критерии остановки

После каждого раунда — оценить, нужен ли следующий:

| После раунда | Остановиться если... | Продолжить если... |
|---|---|---|
| **2 (критика)** | Предложения почти идентичны, критика только по деталям | Есть принципиальные расхождения в подходах |
| **3 (ответы)** | Позиции сблизились, оба скорректировали планы — **стандартная остановка** | Есть конкретный неразрешённый спор (например, A говорит «дублировать», B говорит «извлечь») |
| **4 (финал)** | **Всегда останавливаться.** Максимум 4 раунда. | — |

**По умолчанию останавливаться после Раунда 3.** Раунд 4 запускать только если в ответах (Раунд 3) есть конкретное бинарное разногласие, которое Оппонент может разрешить аргументированно.

### Раунд 2: Критика (SendMessage → Оппонент)

После завершения всех трёх агентов:

```
SendMessage(
  to="opponent",
  prompt="""
Вот два предложения для критики:

## Предложение Архитектора
{полный текст результата Agent 1}

## Предложение Прагматика
{полный текст результата Agent 2}

Критикуй каждое предложение конкретно, с примерами из кода.

## Формат ответа
**Слабые места Архитектора:** (список)
**Слабые места Прагматика:** (список)
**Риски:** (общие для обоих)
**Рекомендация:** (что взять из каждого предложения)
"""
)
```

### Раунд 3: Ответ на критику (SendMessage → Архитектор и Прагматик ПАРАЛЛЕЛЬНО)

После получения критики от Оппонента — отправить её обоим в одном сообщении (параллельно):

```
SendMessage(
  to="architect",
  prompt="""
Оппонент раскритиковал твоё предложение:

{критика Оппонента}

Ответь на критику:
1. С чем согласен — скорректируй свой план
2. С чем не согласен — аргументируй
3. Дай ФИНАЛЬНУЮ версию своего предложения
"""
)
```

```
SendMessage(
  to="pragmatist",
  prompt="""
Оппонент раскритиковал твоё предложение:

{критика Оппонента}

Ответь на критику:
1. С чем согласен — скорректируй свой план
2. С чем не согласен — аргументируй
3. Дай ФИНАЛЬНУЮ версию своего предложения
"""
)
```

### Раунд 4 (опционально): Финальная оценка (SendMessage → Оппонент)

Если ответы Архитектора и Прагматика содержат существенные изменения:

```
SendMessage(
  to="opponent",
  prompt="""
Архитектор и Прагматик ответили на твою критику:

## Ответ Архитектора
{текст}

## Ответ Прагматика
{текст}

Дай финальную оценку: какой подход лучше и почему?
"""
)
```

Если позиции сблизились после Раунда 3 — пропустить Раунд 4 и перейти к синтезу.

## Шаг 4.5. Логировать сырые ответы агентов

Лог-файл: `tasks/logs/TASK-NNN-brainstorm-team-log.md`. Директория `tasks/logs/` уже существует.

**Перед записью** получить точное время через `date '+%Y-%m-%d %H:%M:%S'` (bash).
В PowerShell (opencode на Windows): `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`.

- Если файл **не существует** — создать через **Write** с заголовком и первой сессией.
- Если файл **уже существует** — **дописать** новую сессию в конец через **Edit** (добавить после последней строки).

Формат каждой сессии:

```markdown
---

# Сессия: YYYY-MM-DD HH:MM:SS

Модели: Архитектор (opus) / Прагматик (sonnet) / Оппонент (sonnet)
Раунды: N

## Раунд 1: Исследование и предложения

### Архитектор (opus)
{полный текст}

### Прагматик (sonnet)
{полный текст}

### Оппонент (sonnet) — наблюдения
{полный текст}

## Раунд 2: Критика

### Оппонент (sonnet) — критика предложений
{полный текст}

## Раунд 3: Ответ на критику

### Архитектор (opus)
{полный текст ответа}

### Прагматик (sonnet)
{полный текст ответа}

## Раунд 4: Финальная оценка (если был)

### Оппонент (sonnet)
{полный текст}
```

Заголовок файла (только при создании):

```markdown
# Brainstorm Team Log: TASK-NNN — {название задачи}
```

В opencode в строке «Модели» вместо opus/sonnet указывай модель текущей сессии.

## Шаг 5. Синтезировать и записать результат

На основе дискуссии сформировать финальный план и **записать его в файл задачи** (секция `## План реализации`):

```markdown
## План реализации

> Сформирован через командный брейншторм (Agent Teams: Архитектор/Прагматик/Оппонент, N раундов)

### Выбранный подход
{1-2 предложения — консенсус команды}

### Шаги
1. ...
2. ...

### Файлы
- `path/to/file.py` — что менять

### Дискуссия (краткое резюме)
- **Архитектор** предложил: ...
- **Прагматик** предложил: ...
- **Оппонент** указал на: ...
- **Раунд 3 (ответы):** ...
- **Консенсус:** ...
```

**НЕ перезаписывать** существующие секции файла задачи (Описание, Чеклист, Заметки).
Если секция `## План реализации` уже есть — заменить её.

## Шаг 6. Показать результат пользователю

Вывести краткое резюме:
- Какой подход выбран и почему
- Ключевые точки дискуссии
- Сколько раундов прошло, были ли принципиальные разногласия
- Сколько файлов затронуто
