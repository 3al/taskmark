Создай новую задачу в Task Management системе проекта.

## Аргументы

Что скилл принимает — в `argument-hint` его заголовка. Аргументы **позиционные**:
первый имеет форму, остальное разбирается по описанию шагов.

**`--info`** (а также `--help`, `-h`, `?`) — покажи сигнатуру и ничего не выполняй:
что скилл делает, что принимает, два примера вызова, чего он делать не станет.

**Первый токен похож на флаг** (`--что-угодно`, `-x`, `?`), но это не `--info`, —
он не содержимое и не идентификатор. Покажи ту же сигнатуру и скажи, что такого
аргумента нет. **Не угадывай смысл**: именно так заводится задача с названием
`--help` и выпускается не та версия.

Первый токен подошёл — дальше всё как описано ниже, включая свободный текст.

## Шаг 1. Получить название и эпик

Разбери аргументы вызова:
- **Первый аргумент** (обязательный) — название задачи
- **Второй аргумент** (опциональный) — **ключ эпика** (Jira-ключ вида `E056-18500`), связывающий несколько задач

Если название передано — использовать как есть, перейти к Шагу 2.

Иначе — использовать `AskUserQuestion`/`question` с одним вопросом:
- Вопрос: "Как назвать задачу?"
- Предложи 2–3 варианта на основе контекста текущего разговора (если есть)
- Пользователь выберет один или введёт свой через "Other"

Эпик **не спрашивай отдельно**: он либо передан вторым аргументом, либо его нет. Эпик идентифицируется по Jira-ключу; **имя эпика не пишется в заголовок задачи** — оно хранится в реестре `tasks/epics.md` (см. Шаг 4).

## Шаг 2. Уточнить параметры (AskUserQuestion/question)

Задай **одним вызовом** 2–3 вопроса:

**Q1: Тип задачи** (header: "Тип") — список спрашивай у скрипта
(`py tasks/set_status.py --types`), а не подставляй по памяти:

- `Новый функционал` (`feature`) — добавить новую возможность
- `Баг` (`bug`) — что-то сломано или работает неправильно
- `Рефакторинг` (`refactor`) — улучшение структуры без изменения поведения
- `Уборка` (`cleanup`) — удалить мёртвый код, упростить, унифицировать
- `Обсуждение` (`discussion`) — не про код: разобрать решение с агентом,
  по итогам может родиться задача
- `Дизайн` (`design`) — внешний вид и поведение интерфейса

Тип остаётся в задаче (поле `type:`) и задаёт её чеклист.

**Q2: Критерии приёмки** (header: "Критерии")
- `TDD: RED → GREEN → ALL TESTS PASS` (Рекомендуется) — стандарт для большинства задач
- `Только ручная проверка` — для задач без тестируемой логики (UI-только, документация)
- Пользователь может ввести своё через "Other"

**Q3: Зависимости** (header: "Зависимости") — только если в контексте упоминались другие задачи
- `Нет` (Рекомендуется)
- Через "Other" пользователь укажет `TASK-NNN`

## Шаг 3. Описание

Если описание было явно дано в разговоре — использовать его.

Иначе — сгенерируй описание самостоятельно на основе названия и типа задачи. Описание должно отвечать на вопросы: **что сделать** и **зачем**. Не спрашивай у пользователя — генерируй сам, он сможет скорректировать потом.

**Оформи текст, а не вываливай простынёй** — задачу будет читать человек:

- абзац — одна мысль, между абзацами пустая строка;
- перечисления (варианты, условия, затронутые файлы) — списком;
- `**жирным**` — ключевое решение и ограничение, `` `код` `` — имена файлов, полей, команд;
- длинное описание разбей подзаголовками `###`, короткому хватит пары абзацев.

Это касается и текста, пришедшего от пользователя одной строкой: приведи его в
читаемый вид, не меняя смысла.

## Шаг 4. Зарегистрировать эпик и запустить скрипт

Если эпик указан — сначала убедись, что он есть в реестре `tasks/epics.md`:
1. Прочитай `tasks/epics.md`
2. Если ключ эпика уже есть в разделе «Список эпиков» — переходи к запуску скрипта
3. Если ключа нет — спроси у пользователя **название эпика** одним вопросом, затем добавь запись в раздел «Список эпиков» (замени `_(нет)_` при первой записи):
   ```
   ## <ключ> — <название>
   <краткое описание (опционально)>
   ```

Запусти скрипт создания:

```bash
python3 tasks/create_task.py -t "Название" -d "Описание" -c "Критерии" --type <тип> [-e "КЛЮЧ_ЭПИКА"]
```

**`--type` передавай всегда** — это ответ на Q1. Тип ложится в поле `type:`
задачи и определяет её чеклист; забыл флаг — получишь `feature` и чеклист
не по делу, а на доске метку не того цвета.

Флаг `-e` передавай **только если эпик указан**. Эпик НЕ добавляется в заголовок задачи — он попадает только в поле `epic:` frontmatter.

Задача от чего-то зависит (ответ на Q3) — добавь `-b TASK-NNN`: зависимость
живёт **двумя** концами (`blocked_by` у новой задачи и `blocks` у блокера), и
скрипт проставляет **обе** стороны. Руками поля не пиши — разъедутся.

Скрипт автоматически:
- Выбирает следующий номер TASK-NNN
- Создаёт `tasks/TASK-NNN-slug.md` (с полями `epic:` и `type:`)
- Подставляет чеклист под тип задачи
- Добавляет в `tasks/board.md` — в рубрику раздела приёма по типу задачи
  («Баги» для `bug`, «Обсуждения» для `discussion`); нет такой рубрики —
  в конец раздела
- Проставляет обе стороны зависимости, если передан `-b`

**Чеклист руками не переписывай** — его состав задаёт `--type`. Тип поставлен
мимо — не правь файл, а позови скрипт: `py tasks/set_status.py TASK-NNN --type <тип>`.

## Шаг 5. Показать результат

Прочитай итоговый файл задачи и покажи пользователю:
- ID и название (TASK-NNN · Название)
- Путь к файлу
- Описание и критерии

Предложи: "Если хочешь что-то дополнить — скажи, отредактирую файл."

## Важно

- Не редактируй `board.md` вручную — скрипт делает это автоматически
- Описание генерируй сам — не задавай лишних вопросов пользователю
- Эпик хранится в задаче **только ключом** в поле `epic:` frontmatter; имя эпика — в едином реестре `tasks/epics.md`. Не дублируй имя/ключ эпика в заголовок задачи
