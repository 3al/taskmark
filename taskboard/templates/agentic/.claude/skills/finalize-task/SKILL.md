Финализируй задачу: обнови статус, доску.

## Шаг 0. Определить режим

- Если в аргументах есть `--review` (или пользователь явно просит ревью — «на ревью», «отправь на ревью», «готово к ревью») → **режим review**.
- Если в аргументах есть `--testing` (или пользователь просит тестирование — «на тестирование», «отправь тестировщику», «на стенд», «переведи в testing») → **режим testing**.
- Иначе → **режим completed** (по умолчанию).

Параметры режима:

| Режим | Целевой статус | Целевой раздел board.md | Заметка агента |
|---|---|---|---|
| completed | `completed` | `## Completed` | `задача финализирована` |
| review | `review` | `## Review` | `переведена на ревью` |
| testing | `testing` | `## Testing` | `переведена на тестирование` |

Остальной флоу (чтение, чекбоксы, история коммитов) одинаков для всех режимов.

## Шаг 1. Определить задачу

Если аргумент TASK-NNN передан — использовать его. Флаги `--review`/`--testing` отбросить при поиске файла.

Иначе — найди задачу в текущем контексте разговора (последняя упоминавшаяся TASK-NNN).

Если задача всё ещё неясна — используй инструмент вопроса (Claude Code: `AskUserQuestion`; opencode: `question`):
- Q: "Какую задачу финализировать?"
- В режиме completed предложи варианты из `tasks/board.md` (раздел Testing или Review).
- В режиме review предложи варианты из раздела Development.
- В режиме testing предложи варианты из раздела Development (или Review).

## Шаг 2. Прочитать текущее состояние

Прочитай файл задачи `tasks/TASK-NNN-*.md` и `tasks/board.md`.

## Шаг 3. Уточнить финальную заметку

Задай **одним вызовом** вопрос через инструмент вопроса:

**Q1: Финальная заметка агента** (header: "Заметка") — только если есть что добавить
- `Пропустить` (Рекомендуется) — если ход работы уже отражён в заметках
- `Добавить итоговую заметку` — пользователь опишет через "Other"

## Шаг 4. Сменить статус

Статус меняется **одним вызовом скрипта** — он правит и frontmatter, и board.md
(переносит строку в целевой раздел первой, обновляет хвост `· АГЕНТ · дата`,
возвращает `_(нет)_` в опустевший раздел):

```
py tasks/set_status.py TASK-NNN <целевой статус> --agent "<АГЕНТ (модель)>"     (Windows)
python3 tasks/set_status.py TASK-NNN <целевой статус> --agent "<АГЕНТ (модель)>"
```

Целевой статус — из таблицы режима: `completed`, `review` или `testing`.

Если скрипта в проекте нет — правь вручную оба места: `status:` во frontmatter и
строку задачи в целевом разделе первой строкой, с хвостом `· АГЕНТ (модель) · YYYY-MM-DD`;
в опустевшем разделе оставь `_(нет)_`. Формат строки:
```
- TASK-NNN · [Название задачи](имя-файла.md) · АГЕНТ (модель) · YYYY-MM-DD
```

## Шаг 5. Обновить файл задачи

В файле `tasks/TASK-NNN-*.md`:
1. Все чекбоксы `- [ ]` → `- [x]` (во всех режимах — работа агента завершена, чекбоксы проставляются)
2. Добавить финальную заметку агента в раздел "Заметки агента" (текст заметки — из таблицы режима):
   `<АГЕНТ (модель)>: YYYY-MM-DD: <заметка режима>`
   (если пользователь добавил свой текст — включи его)

## Шаг 6. Заполнить «Историю коммитов»

Секция «История коммитов» в файле задачи должна содержать все коммиты по задаче. Порядок:

1. Выполни `git status` — проверь, есть ли **незакоммиченные** правки по задаче.
2. Если правки есть — спроси пользователя через инструмент вопроса:
   - header: "Коммит финализации"
   - Q: "Есть незакоммиченные правки по задаче. Закоммитить их сейчас?"
   - Варианты: "Да, закоммить" (пользователь даст сообщение / агент предложит) / "Нет, я закоммичу сам позже"
3. Собери коммиты задачи через `git log`:
   ```bash
   # По Jira-ключу из frontmatter `epic:` или по номеру задачи
   git log --all --pretty=format:"%h|%ci|%s" --grep="<JIRA-KEY>" --no-merges | sort -k2
   ```
   Сортировка по дате — хронологический порядок.
4. Если секции «История коммитов» в файле задачи нет — создай её в конце файла по образцу `tasks/_TEMPLATE.md`.
5. Заполни/обнови секцию списком коммитов. Формат каждой строки:
   ```
   - `<short-hash>` <сообщение коммита>
   ```
   - short-hash — 7 символов
   - Сообщение — как в `git log` (без trailing newline)
   - Порядок — хронологический (старые в начале, свежие в конце)
6. **Merge-коммиты не включай** — только meaningful changes с фактическими правками.

## Шаг 7. Обновить Knowledge Vault

Если в рамках задачи были выяснены новые знания о сервисе (архитектура, паттерны, бизнес-правила), которых нет в `vault/`:

1. Определи, какие знания стоит сохранить
2. Используй skill `write-vault` для создания/обновления заметок
3. Если знаний для волта нет — пропустить этот шаг

Критерий: если при следующей задаче на эту же тему агенту пришлось бы заново изучать тот же код — знание стоит сохранить.

**Концепция парных заметок (обязательна):** для новой бизнес-фичи/эндпоинта создаются **две связанные заметки**, а не одна:

- **business** (`vault/<domain>/<verb>-<domain>.md`, напр. `list-inventory.md`) — что это, зачем, бизнес-правила (семантика полей, ограничения, коды ошибок). Frontmatter: `note-type: business`, `impl: "[[<code-note>]]"`
- **code** (`vault/<domain>/api-<...>.md`, напр. `api-post-inventory-list.md`) — реализация: файлы, поток данных, паттерны, разбор «почему так». Frontmatter: `note-type: code`, `concept: "[[<business-note>]]"`

Не ссылаться из code-заметки фичи на общий `README` домена через `concept:` — `concept:` указывает на свою парную business-заметку. Пример пары: `wanted-inventory.md` + `api-post-inventory-id-wanted.md`.

## Шаг 8. Сообщить итог

Выведи краткое резюме (статус — из режима):
```
✓ TASK-NNN · [Название] → completed   (или → review, или → testing)
  Board: обновлена
```

## Важно

- Никогда не редактируй `board.md` так, чтобы одна задача оказалась в двух разделах
- Заметку агента добавляй в конец раздела "Заметки агента", не заменяй существующие
- **При каждом коммите** по задаче (в т.ч. финальном): добавляй строку в секцию **«История коммитов»** файла задачи (если секции нет — создай в конце файла по образцу `tasks/_TEMPLATE.md`). Формат: `` - `<short-hash>` <сообщение коммита> ``, хронологически (свежие — в конец). См. правила проекта § «Правила работы с задачей».
