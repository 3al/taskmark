Продвинь задачу вперёд по пайплайну: обнови статус, доску.

## Аргументы

Что скилл принимает — в `argument-hint` его заголовка. Аргументы **позиционные**:
первый имеет форму, остальное разбирается по описанию шагов.

**`--info`** (а также `--help`, `-h`, `?`) — покажи сигнатуру и ничего не выполняй:
что скилл делает, что принимает, два примера вызова, чего он делать не станет.

**Первый токен похож на флаг** (`--что-угодно`, `-x`, `?`), но это не `--info`, —
он не содержимое и не идентификатор. Покажи ту же сигнатуру и скажи, что такого
аргумента нет. **Не угадывай смысл**: именно так заводится задача с названием
`--help` и выпускается не та версия.

Первый токен подошёл — дальше всё как описано ниже, включая свободный текст.

## Шаг 0. Узнать пайплайн проекта

Жизненный цикл настраивается per-project: у одного проекта есть ревью, у другого нет,
где-то между разработкой и стендом стоит локальная проверка. **Не подставляй имена
статусов по памяти** — спроси у скрипта:

```
py tasks/set_status.py --targets TASK-NNN            (Windows)
python3 tasks/set_status.py --targets TASK-NNN
```

Лаунчера `py` может не быть (Python из Microsoft Store его не ставит) —
тогда та же команда через `python`. Подробнее — в правилах проекта,
раздел «Чем запускать скрипты».

Ответ (JSON):
- `current` — текущий статус задачи
- `forward` — куда можно двинуть вперёд (включая съезды вроде отмены)
- `next` — ожидаемый следующий шаг маршрута; именно его предлагай первым
- `pipeline` — все статусы проекта с подписями
- `actions` — цели действий скиллов

`next` учитывает тип задачи: у обсуждения и код-ревью релизного хвоста нет, и шаг
ведёт мимо него. **Не выправляй это по порядку статусов** — пропуск здесь не сбой,
а вид работы.

**Где кончается работа над задачей — тоже отсюда, а не из имени статуса.** Задана
`actions.release_draft` (подготовка текстов релиза) — работа кончается в статусе
**перед** ней: дальше задачу ведёт уже выпуск. Не задана — работа кончается
в терминальном статусе.

Различие не косметическое: с релизным хвостом `done` наступает при выпуске, и
закрывает задачу уже релизный скилл — через дни, в другой сессии. Хвосты задачи —
чекбоксы, история коммитов, чужие пометки простоя — прибираются **здесь**, обычно
сразу после того, как человек подтвердил проверку: коммит к этому моменту как раз
и разрешён. При переходе именно в этот статус скрипт печатает `[!]` с тем, что
осталось, — это подсказка, а не запрет.

<!-- vault -->
**Знание в волт пишется раньше** — при уходе из рабочего статуса; это делает
скилл `handoff-task`, и скрипт напоминает о нём в тот же момент. Причина не в
том, что здесь контекст потерян (обычно он жив), а в том, что **финализации может
не случиться вовсе**: карточку переносят мышью, задача уезжает без агента, и
знание не запишется уже никогда. Передача же неизбежна — без неё задача из работы
не уходит. Здесь остаётся проверить, что шаг не пропустили (шаг 7).
<!-- /vault -->

**Задача ещё в рабочем статусе (`actions.start`), и цель — следующий шаг?** Это
передача на проверку, а не финализация: у неё свой скилл — `handoff-task`. Он
закроет чекбоксы работы, сохранит знание и скажет человеку, что проверять.
Вызвали финализацию словами вроде «на тестирование» — предложи передачу.

Скрипта нет (старый проект) — прочитай `tasks/board.md` и работай по его разделам.

## Шаг 1. Определить задачу

Если аргумент TASK-NNN передан — использовать его.

Иначе — найди задачу в текущем контексте разговора (последняя упоминавшаяся TASK-NNN).

Если задача всё ещё неясна — используй инструмент вопроса (Claude Code: `AskUserQuestion`;
opencode: `question`): Q «Какую задачу финализировать?», варианты — задачи из разделов
доски, которые в пайплайне идут до терминального (то есть работа по ним ещё не закрыта).

## Шаг 2. Прочитать текущее состояние

Прочитай файл задачи `tasks/TASK-NNN-*.md` и `tasks/board.md`.

## Шаг 3. Выбрать целевой статус и уточнить комментарий

Если пользователь назвал цель словами («на ревью», «на стенд», «закрой») — сопоставь
её с `forward` по подписям из `pipeline` и бери без вопросов.

Иначе задай **одним вызовом** вопрос через инструмент вопроса:

**Q1: Куда двигаем** (header: "Статус") — варианты из `forward`, первым `next`
с пометкой «(Рекомендуется)». Съезды (`offramp`, например отмена) показывай последними.

**Q2: Итоговый комментарий** (header: "Комментарий") — только если есть что добавить
- `Пропустить` (Рекомендуется) — если ход работы уже отражён в комментариях
- `Добавить итоговый комментарий` — пользователь опишет через "Other"

Своего мнения о «правильном» следующем шаге у скилла нет: маршрут задаёт пайплайн
проекта, а прыжок вперёд (простая задача, хотфикс) — законный ход, не ошибка.

**Цель — съезд (`offramp`, отмена)? Спроси причину** тем же вызовом вопроса
(header: «Причина», варианты — по контексту разговора, свой текст через «Other»).
Без неё скрипт откажет: из отмены не возвращаются, и «почему» остаётся в файле.
Причину не выдумывай — она нужна человеку, который придёт к задаче позже.

## Шаг 4. Обновить файл задачи

В файле `tasks/TASK-NNN-*.md`:
0. **Взгляни на описание и критерии приёмки.** Их правят из окна доски прямо по
   ходу работы, и текст пользователя приходит без разметки: слипшиеся абзацы,
   перечисления через запятую, оборванный список. Поехало — **оформи** по
   правилам проекта («Как писать текст задачи»), меняя только разметку:
   формулировки автора остаются дословно.

   Правило «оформляет тот, кто берёт задачу в работу» срабатывает один раз, при
   старте, — правку, внесённую позже, причесать больше некому.
1. Секция «Чеклист», если она есть: отметь `- [x]` сделанное, а пункт, который
   выполняться не будет, **удали**. Проставлять галочки подряд «раз работа
   кончилась» нельзя — тогда план перестаёт что-либо значить.

Итоговый комментарий отдельным вызовом писать не нужно: он уйдёт вместе с
переводом статуса одной командой (шаг 7).

## Шаг 5. Заполнить «Историю коммитов»

Секция «История коммитов» должна содержать все коммиты по задаче. Есть
незакоммиченные правки (`git status`) — спроси, коммитить ли их сейчас.

Собери коммиты и заполни секцию (нет её — создай в конце файла по образцу
`tasks/_TEMPLATE.md`):

```bash
# По Jira-ключу из frontmatter `epic:` или по номеру задачи
git log --all --pretty=format:"%h|%ci|%s" --grep="<JIRA-KEY>" --no-merges | sort -k2
```

Строка — `` - `<short-hash>` <сообщение коммита> `` (7 символов, сообщение как
в `git log`), порядок хронологический: свежие в конец. **Merge-коммиты не
включай.**

## Шаг 6. Проверить, что знание сохранено

**Записывать знание в волт — не работа этого скилла**: его момент раньше, при
уходе из рабочего статуса, там это делает `handoff-task`.

Здесь нужно убедиться, что шаг не пропущен. Задачу двигали мимо (рукой на доске,
коротким вызовом скрипта) и по её теме осталось знание, которого нет в `vault/`, —
скажи человеку и запиши, что помнишь, скиллом `write-vault`, отметив в заметке,
что она писалась задним числом. Знаний задача не дала — шаг пропускается молча.
<!-- /vault -->

## Шаг 7. Сменить статус — последним действием

**Статус меняется, когда всё остальное уже сделано.** Он публикует факт «задача на
этом этапе», и публиковать его раньше, чем файл приведён в порядок, значит соврать
на доске. Требования этапа проверяются ровно в этот момент: незаполненная «История
коммитов» или незакрытый чеклист остановят перевод — и правильно остановят, но
чинить это надо было выше, а не после отказа.

Статус меняется **одним вызовом скрипта** — он правит и frontmatter, и board.md
(переносит строку в целевой раздел первой, обновляет хвост `· АГЕНТ · дата`,
возвращает `_(нет)_` в опустевший раздел):

```
py tasks/set_status.py TASK-NNN <целевой статус> --agent "<АГЕНТ (модель)>" --note "переведена в <подпись статуса>"   (Windows)
python3 tasks/set_status.py TASK-NNN <целевой статус> --agent "<АГЕНТ (модель)>" --note "…"
```

Этап может спрашивать **исполнителя** — тогда без имени перевод не выполнится.
Имя знает только человек: спроси его, предложив известные
(`set_status.py --assignees`), и передай тем же вызовом — `--assignee "Имя"`.
Никого не выдумывай.

Комментарий идёт тем же вызовом: время скрипт берёт из системы, строку ставит в конец
секции:

```
- **2026-03-02 23:59** · Claude Sonnet 4.6 · переведена в <подпись статуса>
```

**Модель — своя**, из текущей сессии, а не скопированная из соседней строки; текст
пользователя, если он его дал, включи в тот же комментарий. Скрипта в проекте нет —
пиши строку руками в том же формате, в конец секции.

Скрипт печатает `[i] минуя <статусы>`, если шаг перепрыгнул часть маршрута —
это информация для лога, а не ошибка.

Отмена (съезд) — с причиной, иначе отказ:

```
py tasks/set_status.py TASK-NNN <съезд> --agent "<АГЕНТ (модель)>" --reason "дублирует TASK-002"
```

Если скрипта в проекте нет — правь вручную оба места: `status:` во frontmatter и
строку задачи в целевом разделе первой строкой, с хвостом `· АГЕНТ (модель) · YYYY-MM-DD`;
в опустевшем разделе оставь `_(нет)_`. Формат строки:
```
- TASK-NNN · [Название задачи](имя-файла.md) · АГЕНТ (модель) · YYYY-MM-DD
```

## Шаг 7.1. Сказать, кого задача разблокировала

Поле `blocks` во frontmatter закрываемой задачи перечисляет тех, кто её ждал.
Если оно не пустое (`~` — пусто), скажи об этом в итоге: эти задачи, вероятно,
пора освобождать.

- Задача доехала до конца маршрута — её собственный простой скрипт снял сам,
  а вот **чужие пометки остаются**: их снимает человек или следующий агент.
- Команда для снятия — у ждавшей задачи, а не у этой:
  `py tasks/set_status.py TASK-MMM --unblock TASK-NNN`.
- Полная картина простоя по проекту — `py tasks/set_status.py --stalled`.

## Шаг 8. Сообщить итог

Выведи краткое резюме:
```
✓ TASK-NNN · [Название] → <целевой статус>
  Board: обновлена
  Разблокированы: TASK-MMM (если ждали)
```

Хочешь подсказать, что дальше в очереди, — **сначала спроси её у скрипта**:

```
py tasks/set_status.py --queue             (Windows)
python3 tasks/set_status.py --queue
```

Пока задача делалась, доску правили: через UI, другим агентом, из другой ветки.
Очередь, названная по памяти сессии, почти наверняка врёт — либо спроси, либо
не называй вовсе.

## Важно

- Никогда не редактируй `board.md` так, чтобы одна задача оказалась в двух разделах
- **Очередь — только из `--queue`**, не из памяти: это последняя реплика по задаче,
  и ошибка в ней уводит следующую сессию не туда
- Комментарий пиши командой `--note`: он встаёт в конец раздела «Комментарии»
  с системным временем. Существующие строки не заменяй и не переставляй
- **Заголовки секций не сноси**, «История коммитов» остаётся последней секцией файла.
  Смена статуса печатает `[!] …`, если структура разъехалась — почини сразу
- **При каждом коммите** по задаче: строка в секцию **«История коммитов»** файла задачи — формат в правилах проекта, § «Правила работы с задачей». Пустая секция не пропадёт незамеченной: скрипт скажет о ней при уходе с этапа работы.
