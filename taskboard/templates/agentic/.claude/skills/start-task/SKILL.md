Возьми задачу в работу: статус → доска → контекст → реализация.

## Шаг 1. Определить задачу

Если первый аргумент передан (TASK-NNN) — использовать его.

Иначе — найди задачу в текущем контексте разговора (последняя упоминавшаяся TASK-NNN).

Если задача всё ещё неясна — используй инструмент вопроса (Claude Code: `AskUserQuestion`; opencode: `question`):
- Q: "Какую задачу начать?"
- Предложи варианты из `tasks/board.md` (раздел Backlog)

Реши файл через `glob`: `tasks/TASK-NNN-*.md`.

## Шаг 1.1. Дополнительный контекст задачи

Если передан второй аргумент (дополнительный контекст задачи):
- Запомни его как дополнение к описанию задачи.
- Он может содержать: уточнения по реализации, ссылки на MR/коммиты/тикеты, конкретные архитектурные решения, требования к совместимости, ограничения, приоритеты и т.д.
- Учитывай этот контекст при формировании плана (Шаг 7) и реализации.

Выведи пользователю подтверждение: «Дополнительный контекст принят: <текст>».

## Шаг 2. Прочитать текущее состояние

Прочитай файл задачи `tasks/TASK-NNN-*.md` и `tasks/board.md`.

Если `status` уже `development`/`review`/`testing`/`completed` — предупреди пользователя и спроси, действительно ли стартовать/продолжить.

## Шаг 3. Понять задачу

Извлеки из файла: `title`, `epic`, описание, критерии приёмки, чеклист.
Прочитай `tasks/epics.md` и определи **имя эпика** (если эпик указан).
Учти **дополнительный контекст задачи** (если был передан вторым аргументом) — он дополняет/уточняет описание.

Сформулируй для себя: **что** сделать, **зачем**, какие ограничения/критерии.

## Шаг 4. Собрать знания из Knowledge Vault

Это ключевая ценность скилла — не начинать с нуля, а переиспользовать известное.

1. Прочитай `vault/SYS/taxonomy.md` — доступные домены и теги.
2. Определи **кандидатов-доменов** по:
   - **имени эпика** из `tasks/epics.md` (оно часто прямо указывает на домен волта);
   - **ключевым словам** из title/description.
3. Для каждого кандидата прочитай заметки в `vault/<domain>/` — **сначала `*-business`, затем `*-code`**.
4. Если домен неочевиден — сделай `grep` по `vault/` по ключевым словам задачи.
5. Зафиксируй коротко: какие бизнес-правила, паттерны, контракты, ключевые файлы уже известны.
6. Если релевантных заметок нет — явно отметь: «в волте нет релевантных заметок».
<!-- /vault -->

## Шаг 5. Перевести в development

В файле `tasks/TASK-NNN-*.md`:
1. `status: development`
2. Добавь стартовую заметку агента в раздел «Заметки агента» (первой строкой):
   `<АГЕНТ (модель)>: YYYY-MM-DD: старт задачи. План: <кратко>`.

В `tasks/board.md`:
1. Найди строку TASK-NNN в текущем разделе (обычно Backlog) и **перемести** её в раздел `## Development` **первой строкой**.
2. Допиши/обнови хвост строки: `· <АГЕНТ (модель)> · YYYY-MM-DD`.
3. Если раздел, из которого убрал задачу, стал пустым — поставь `_(нет)_`.
4. Никогда не оставляй задачу в двух разделах одновременно.

АГЕНТ (модель) — твоё текущее обозначение.

## Шаг 6. Изучить кодовую базу

- Найди `grep`/`glob` существующие похожие реализации, сервисы, контракты, репозитории.
- Сверься с правилами проекта (`AGENTS.md` / `CLAUDE.md`): архитектура затрагиваемых слоёв, workflow после изменений.
- **Переиспользуй** существующий код — не дублируй.

## Шаг 7. Представить план и приступить к реализации

Кратко покажи пользователю: суть задачи + дополнительный контекст (если был) + находки в коде + план реализации.

Затем реализуй, следуя правилам проекта:
- **TDD** там, где есть тестируемая логика (RED → GREEN → все тесты зелёные). Если автотесты что-то не покрывают — ручная проверка через доступные интерфейсы (HTTP, консоль, UI).
- **Деструктивные операции с данными** (БД, файлы, продакшн-контуры) — только с подтверждения пользователя.
- **Не коммить** без явного запроса пользователя.
- **Если план расходится с обсуждённым или требует архитектурных решений** — остановись и согласуй.
- В ходе работы добавляй **компактные заметки агента** в файл задачи (формат и лимит — см. правила проекта).

## Шаг 8. Проверка после реализации

- Запусти проверки проекта (линтеры, статический анализ, тесты — согласно правилам проекта).
- Ручная проверка через HTTP/консоль/UI, если применимо.

## Важно

- Скилл = подготовка контекста + старт.
