name: release
description: >
   Подготовить выпуск версии: показать готовые задачи, отобрать состав релиза,
   написать пользовательский текст изменений по каждой задаче, собрать changelog
   и выпустить, если в проекте настроен скрипт выпуска.
   Используй когда пользователь говорит: "готовь релиз", "собери релиз",
   "выпускаем версию", "release", "подготовь выпуск", "что пойдёт в релиз".
argument-hint: "[major|minor|patch]"

Подготовь выпуск: состав → тексты → changelog → выпуск.

Скилл делает всё, кроме трёх решений: **состав релиза, формулировки для
пользователей и разряд версии** остаются за человеком. Остальное между ними
происходит без него.

## Аргументы

Что скилл принимает — в `argument-hint` его заголовка. Аргументы **позиционные**:
первый имеет форму, остальное разбирается по описанию шагов.

**`--info`** (а также `--help`, `-h`, `?`) — покажи сигнатуру и ничего не выполняй:
что скилл делает, что принимает, два примера вызова, чего он делать не станет.

**Первый токен похож на флаг** (`--что-угодно`, `-x`, `?`), но это не `--info`, —
он не содержимое и не идентификатор. Покажи ту же сигнатуру и скажи, что такого
аргумента нет. **Не угадывай смысл**: именно так заводится задача с названием
`--help` и выпускается не та версия.

Первый токен подошёл — дальше всё как описано ниже, включая свободный текст.

## Шаг 0. Узнать маршрут проекта

Имена статусов и цели действий настраиваются per-project — **не подставляй их
по памяти**:

```
py tasks/set_status.py --list             (Windows)
python3 tasks/set_status.py --list
```

Лаунчера `py` может не быть — тогда та же команда через `python`.

Из ответа нужны три вещи:

- `actions.release_draft` — куда переносить отобранное (подготовка текстов);
- `actions.release_lock` — куда переносить утверждённое;
- `release_script` — чем проект выпускает версии (пусто — своего механизма нет).

### Если релизных этапов нет

`actions.release_draft` или `actions.release_lock` отсутствуют — **останавливайся
сразу**, ничего не трогая:

> В маршруте проекта нет этапов выпуска. Добавьте их в Настройки (⚙) → Жизненный
> цикл: готовый пресет «С релизами» или назначьте действия «Готовить заметки
> релиза» и «Отобрано в релиз» вручную.

### Если цель действия указывает в пустоту

Статуса из `actions.release_draft` нет в `pipeline` — тоже останавливайся:
действие настроено на статус, которого в маршруте больше нет. Назови ключ и
статус, предложи поправить в настройках.

## Шаг 1. Осмотреть все релизные статусы

В выпуск задача попадает **двумя путями**: через этот скилл и мышью на доске.
Второй законен — доска источник правды, и человек вправе положить задачу в релиз
сам. Поэтому смотреть только в пул нельзя: то, что уже лежит дальше по хвосту, —
остатки прошлого запуска или ручные переносы, и это часть выпуска, а не сор.

Прочитай в `tasks/board.md` разделы **трёх** статусов (имена разделов бери из
`pipeline` шага 0, а не по памяти):

| Что | Статус |
|---|---|
| пул готового | статус **перед** `actions.release_draft` (обычно «Готово к выпуску») |
| подготовка текстов | `actions.release_draft` |
| утверждённое | `actions.release_lock` |

**Не называй состав по памяти**: доску правят через UI и другие агенты, снимок
из начала сессии устаревает молча.

Покажи три списка отдельно — номер, заголовок, одна строка сути, — и пометь
задачи, у которых **нет секции «Изменение для пользователя»**: им предстоит
черновик. Пусты все три — выпускать нечего, скажи об этом и остановись.

Спроси, что добавить в выпуск **из пула**. Предложи весь пул как вариант
по умолчанию, но **решает человек**: часть задач может ждать следующего раза.

Задачи из двух других статусов в выпуске **уже есть** — их не выбирают заново.
Человек может вернуть любую из них в пул, если она поехала туда по ошибке.

## Шаг 2. Перенести отобранное и написать тексты

Отобранное из пула переведи в `actions.release_draft` **скриптом** — он правит
и frontmatter, и доску:

```
py tasks/set_status.py TASK-NNN <actions.release_draft> --agent "<АГЕНТ (модель)>"
```

Задачи, которые уже лежали в подготовке или в утверждённом, переносить **не
нужно** — они на месте. Дальше все задачи выпуска равны: и перенесённые сейчас,
и оказавшиеся в релизных статусах до тебя.

Черновик пишется тем, у кого секции **«Изменение для пользователя»** нет вовсе:

1. Добавь секцию **после «Описания»**, перед «Чеклистом»; «История коммитов»
   остаётся последней секцией файла.
2. Заполни её черновиком.

**Признак — отсутствие секции, а не её пустота.** Пустая секция — это принятое
решение «сказать нечего» (см. ниже): **не перезаписывай** её и не переспрашивай
про неё, иначе каждый прогон выпуска будет отменять чужое решение.

### Каким должен быть текст

Его прочитает человек, решающий, обновляться ли ему. Он не знает ни вашей
кодовой базы, ни номеров задач.

- **О результате, а не о работе.** Не «переписан `updater.check_remote`», а
  «проверка обновлений больше не ходит в сеть без разрешения».
- **Одно-два предложения.** Подробности живут в описании задачи.
- **Без номеров задач, имён файлов и функций** — они ничего не говорят читателю.
- **Заголовок задачи не годится как есть**: он написан для агента.

### Если сказать пользователю нечего

Рефакторинг, тесты, правки внутренней механики — изменения, которых человек
снаружи не заметит. **Оставь секцию пустой.** Не пиши «Исправление багов»
и подобные пустые формулировки: строка, которая ничего не сообщает, хуже
её отсутствия — она занимает место в changelog и заставляет читателя гадать.

Пустая секция — обычный исход, а не недоделка. Скажи об этом в списке на шаге 3
одной строкой («сюда сказать нечего»), чтобы человек увидел решение и мог с ним
не согласиться.

## Шаг 3. Показать черновики и дождаться правок

**Этот шаг не пропускается никогда**, и общее «катим релиз» его не заменяет:
это согласие начать выпуск, а не одобрение формулировок, которых человек ещё
не видел.

Выведи все тексты одним списком: задача → текст. Скажи прямо, что это
**черновик для правки**, и дождись ответа.

Человек может: принять всё, поправить формулировки, убрать задачу из выпуска
(тогда верни её в пул тем же скриптом).

## Шаг 4. Утвердить состав

**Только после явного ответа человека по текстам** (шаг 3) переведи каждую
задачу подготовки в `actions.release_lock`. Перевод и означает «тексты
утверждены» — сделать его раньше нечем оправдать:

```
py tasks/set_status.py TASK-NNN <actions.release_lock> --agent "<АГЕНТ (модель)>"
```

Теперь в этом статусе лежит ровно то, что поедет ближайшим выпуском.

**Сверься с составом статуса заново** — перечитай его раздел на доске: задача,
попавшая туда мышью, выглядит одобренной, но текста у неё может не быть вовсе.
Нашлись без секции «Изменение для пользователя» — напиши черновик, как на шаге 2,
и покажи. Пустая секция — не этот случай: там решение принято.

## Шаг 5. Собрать changelog

Состав берётся **из статуса `actions.release_lock`** — с доски, а не из списка,
отобранного на шаге 1: между ними человек мог добавить задачу мышью или убрать
свою. Что лежит в утверждённом, то и выпускается.

Из текстов этих задач собери фрагмент в формате Keep a Changelog — группами
**«Добавлено» / «Изменено» / «Исправлено»**.

**Задачи с пустой секцией пропусти** — им сказать нечего.

**Совпавшие тексты схлопни в одну строку.** Несколько задач могут дать один
и тот же результат для пользователя — читателю незачем видеть его дважды.
Схлопывай только **точные совпадения**: похожие формулировки сливать нельзя,
это уже суждение о смысле, а не сборка. Объединил — скажи об этом в отчёте,
чтобы человек знал, почему строк меньше, чем задач.

Заголовок версии **не пиши**: его подставит скрипт выпуска. Твой результат —
только тело секции.

Сохрани фрагмент во временный файл: он передаётся скрипту путём.

## Шаг 6. Выпустить

### Если `release_script` пуст

Останавливайся с результатом — это нормальный исход, а не ошибка:

> Состав отобран, тексты в задачах, changelog собран (показать текст).
> Механизм выпуска в проекте не настроен, поэтому выпускайте как принято у вас.
> После выпуска переведите задачи в терминальный статус.

Скажи заодно, что скрипт выпуска подключается настройкой `release_script`.

### Если `release_script` задан

**Сначала проверка, до вопросов человеку:**

```
py <release_script> --check --bump <разряд>
```

Ответ — json: `current`, `next`, `blockers`. Есть преграды — покажи их списком
и остановись: чинить их по одной, запуская выпуск заново, — худший сценарий.

**Предложи разряд версии с обоснованием.** Это суждение о том, что случится
у пользователя, который обновится не читая:

- **major** — сломается формат его данных или потребуется ручное вмешательство;
- **minor** — появилась возможность, старое работает как работало;
- **patch** — исправления и правки текстов, поведение прежнее.

Назови предлагаемый разряд, причину и получившуюся версию (`next` из ответа).
**Решает человек.**

**После подтверждения:**

```
py <release_script> --apply --bump <разряд> --notes <файл> --tasks TASK-001,TASK-002
```

Ответ — json с `version`, `tag`, `commit`. Провал (`ok: false`) — покажи `error`
и остановись, ничего не трогая дальше.

**Публикация — отдельное подтверждение.** Пуш и тег необратимы для пользователей:

```
py <release_script> --publish
```

## Шаг 7. Закрыть задачи выпуска

Только **после успешной публикации**:

1. Переведи в терминальный статус (последний в `pipeline`, не считая `offramp`)
   **каждую задачу из `actions.release_lock`** — тот же состав, что ушёл
   в changelog. Закроешь список из своей памяти — задача, добавленная мышью,
   останется висеть в релизном статусе после выпуска.
2. Допиши в секцию «История коммитов» каждой задачи строку релизного коммита:
   `` - `<short-hash>` Релиз <версия>``.
3. Добавь комментарий о выпуске:

   ```
   py tasks/set_status.py TASK-NNN --note "выпущено в <версия>" --agent "<своя модель>"
   ```

## Шаг 8. Отчитаться

Коротко: версия, тег, сколько задач вошло, ссылка на changelog. Если что-то
не удалось (например, GitHub Release) — скажи прямо, но не подавай это как
провал выпуска: тег и манифест уже на месте.

## Важно

- **Ничего не выпускай без подтверждения человека** — ни разряд версии, ни пуш.
- **Тексты для пользователей утверждает человек, и шаг 3 не пропускается.**
  Общее «катим релиз» — согласие начать выпуск, а не одобрение формулировок,
  которых он ещё не видел.
- **Состав и тексты берутся с доски и из файлов задач**, а не из памяти сессии.
- **Заголовки секций файла задачи — его структура**: не сноси и не переставляй
  их, «История коммитов» остаётся последней.
- Статусы меняй **только скриптом**: он правит frontmatter и доску за один вызов,
  и они не разойдутся.
- Скрипта выпуска нет — это не повод останавливать подготовку: самая трудоёмкая
  часть работы (состав и тексты) полезна сама по себе.
